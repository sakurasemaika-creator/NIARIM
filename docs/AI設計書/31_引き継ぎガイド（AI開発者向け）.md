## 1. 環境を整える（毎セッション最初にやること）

```bash
export PATH="$PATH:/opt/flutter-sdk/bin"
flutter --version   # Flutter 3.47.2 stable / Dart 3.13.2 を確認
```

`flutter` は既定のPATHに無い。**コンテナが作り直されるとSDKごと消える**ことが
あるので、その場合は同じバージョンのtarballを `/opt/flutter-sdk` へ展開し直す
（バージョンがずれると `dart format` の結果が変わり、リポジトリ全体に
差分が出るため必ず合わせること）。

`root` で実行するため毎回警告が出るが無視してよい。

### コンテナは使い捨て

このリモート実行環境は使い捨てのコンテナで、**未コミットの変更は失われる**。
まとまった単位でこまめにコミットすること。過去に一度、数時間ぶんの作業を
コンテナ再起動で丸ごと失っている。

## 2. 作業サイクル（1タスクぶんの型）

```bash
# 1. 実装
# 2. 整形（手で字下げを合わせない）
dart format lib test tool
# 3. 静的解析：ベースラインは 0 issues
flutter analyze
# 4. テスト：ベースラインは 704 tests 全成功
flutter test
# 5. 焼いたPNGを目で見る（後述）
# 6. ドキュメント更新 → コミット → push
```

### ベースラインの意味

- `flutter analyze` は **0 issues**。infoが1件でも増えたら、それは自分が
  足したもの。「元からあった」ということはない。
- `flutter test` は **704 tests 全成功**。増減したら理由を説明できること。

### 整形ツールは呼び出し方に癖がある

**引数を間違えると「整形されていない」と誤検知して全ファイルを別の流儀へ
書き換えてしまう**。必ず次の指定で使う。

| 対象                          | コマンド                                                     |
| ----------------------------- | ------------------------------------------------------------ |
| Dart                          | `dart format lib test tool`                                  |
| Markdown / YAML / JSON / HTML | Prettier 3.8.1（設定ファイル無し＝既定のまま）               |
| ARB（`lib/l10n/*.arb`）       | Prettier に **`--parser json`** を渡す（拡張子から推論不可） |
| XML / plist                   | `@prettier/plugin-xml` 3.4.2 を `--plugin` で明示            |
| Python                        | `ruff format` / `ruff check`                                 |
| Kotlin                        | ktfmt 0.64 の **`--kotlinlang-style`**                       |
| C / C++                       | clang-format の **`--style=Google`**                         |

`dart fix --apply --code=curly_braces_in_flow_control_structures` と
`dart format` は**入れ子のforに対して互いに打ち消し合い収束しない**。
入れ子forの外側は手で波括弧を付けること。

### 多言語（ARB）を触ったら

`lib/l10n/app_*.arb`（ja/en/es/fr/ko/zh/zh_Hant、jaがテンプレート）を編集したら
必ず `flutter gen-l10n` を実行し直す。**機械的な一括置換をしない**こと
（ES/FR等で訳が崩れる）。文言を足したら韓国語・簡体字の**サブセットフォントを
作り直す**（`python3 tool/build_fallback_fonts.py <元フォントのディレクトリ>`）。
作り直し忘れは `test/font_coverage_test.dart` が検出する。

### コミットメッセージの型

日本語で、次の4段構成にするのがこのリポジトリの慣行。

```
<1行要約>

依頼：「<ユーザーの依頼をそのまま引用>」
原因：<調査で分かった、なぜそうなっていたか>
対応：<何をどう変えたか>
検証：<analyze / test の件数、目視した内容>
```

ソースコード中のコメントには仕様書番号・Task番号を**書かない**
（技術的な説明のみ）。経緯は `12_実装チェックリスト.md` とコミット
メッセージに書く。

## 3. 検証のやり方（ここが最重要）

**この環境にはAndroid実機が無い。**そして経験上、
**「テストが緑」は「意図どおり動く」を意味しない。**

このプロジェクトで実際に見つかった不具合のうち、次のものは
**全テストが緑のまま**存在していた。

| 不具合                                                | 見つけた方法            |
| ----------------------------------------------------- | ----------------------- |
| アプリ中のSnackBarの文字が全部、端末標準フォント      | PNGを見た（豆腐だった） |
| 全FilledButtonのラベルが端末標準フォント              | PNGを見た               |
| 「全選択」ボタンが押しても何も起きない                | PNGを見た               |
| キャンバスのツールバーの長押しメニュー5つが全部無反応 | PNGを見た               |
| ジェスチャー選択シートが77pxはみ出して選べない        | ダイアログPNG監査       |
| クイックツール追加が654pxはみ出し登録できない         | ダイアログPNG監査       |
| 回転ハンドルの円が画面端で4px欠けていた               | PNGを4倍に拡大して見た  |
| 拡張描画範囲ONでタップ位置が2倍ずれる（全ツール）     | 実画素を読み出した      |

したがって検証は次の3段構えで行う。**上から順に、省略しない。**

### 段階1：アサーションで機械的に守る

回帰テストは必ず「**修正を元に戻すと落ちること**」を確認する。
両方の状態で通るテストは無意味であり、実際にそれを書いてしまった事故がある
（`ListView.builder` 化の検証で、Element数を数えても検出できなかった）。

### 段階2：操作ウォークスルーでPNGを焼き、1枚ずつ目で見る

手順は `30_AI自律動作確認プロンプト.md` に、他モデルへそのまま渡せる
プロンプトの形でまとめてある。既存の雛形は次のとおり。

| テスト                                           | 出力先                                |
| ------------------------------------------------ | ------------------------------------- |
| `test/selection_tool_walkthrough_test.dart`      | `build/selection-walkthrough/`        |
| `test/extended_drawing_area_selection_test.dart` | `build/extended-area-walkthrough/`    |
| `test/theme_settings_walkthrough_test.dart`      | `build/theme-walkthrough/`            |
| `test/canvas_panel_screenshot_audit_test.dart`   | `build/visual-reaudit/canvas-panels/` |
| `test/dialog_screenshot_audit_test.dart`         | `build/dialog-screenshots/`           |
| `test/all_routes_screenshot_audit_test.dart`     | `build/all-route-screenshots/`        |

ルート単位・ダイアログ単位の監査は**1画面1状態しか撮らない**ため、
「ツールを切り替えて→範囲を囲んで→ドラッグする」のような途中経過は
一切検証されない。新しい機能を足したらウォークスルーを1本足すこと。

### 段階3：疑わしければ実画素を読む

見た目で判断が付かないときは推測しない。`toByteData()` で画素を読み、
重心・範囲・アルファ値を数値で確かめる。
「拡張描画範囲ONでタップ位置が2倍ずれる」はこの方法でしか特定できなかった
（PNGを見ても『何か変』までしか分からない）。

PNGを縮小表示のまま眺めると**細い明朝体が背景に沈んで「コントラスト不足の
不具合だ」と誤読しやすい**。怪しいと思ったら画素値を測るか、`Image.NEAREST`
で3倍程度に拡大すること（実際に誤読しかけた）。

### 実機でしか分からないことは、正直にそう言う

タップの掴みやすさ、ジェスチャーの効き、実際の描画速度、動画コンテナの
再生互換性（AVI等）、ブラシの描き味、ランチャーアイコンの実機での見え方は
コードレビューでは判定できない。「直った」と断定せず
**「直っている可能性が高いが実機要確認」**と報告すること。

## 4. コードの地図

```
lib/
├── main.dart / app.dart / router.dart / app_bootstrap.dart
├── config/          monetization_gate.dart（収益化タイマー）・font_fallback.dart
├── engine/    (29)  ウィジェットツリーの外側で動く純粋な処理
│                    tile_manager / drawing_engine / export_engine /
│                    layer_compositor / mesh_warp_engine / undo_manager /
│                    autofill_engine / bucket_fill_engine / ruler_engine …
├── models/    (37)  Project・Scene・Frame・Layer などのデータ構造
├── services/  (40)  ChangeNotifier群（Providerで配る状態）
│                    project_service / theme_service / settings_service /
│                    brush_service / premium_service / community_service …
│   └── api/         作品広場バックエンドのクライアント層（21エンドポイント）
├── screens/   (73)  画面。canvas/ 配下がいちばん重い
├── widgets/   (27)  画面をまたいで使う部品
├── utils/     ( 7)  color_contrast / reorder_index など純粋関数
└── l10n/           7言語のARBと生成コード
```

### 押さえておくべき構造上の前提

- **`ExportEngine` は `Theme` / `BuildContext` にアクセスできない**
  （ウィジェットツリー外の純粋な描画エンジン）。エンドカードの背景色は
  既定テーマのアクセント色をハードコードしてあり、`tool/gen_app_icon.py`・
  `pubspec.yaml` の `adaptive_icon_background` と**3箇所を同期**する必要がある。
- **キャンバスの座標系は「描画範囲サイズ」**（書き出しサイズ×
  `drawingAreaScale`）。`TileManager` の実寸も選択マスクの寸法もこれ。
  書き出しサイズと混同すると、拡張描画範囲ONのときだけ座標が倍率ぶんずれる
  （実際にそうなっていた）。`canvasPixelSizeOf()` を使うこと。
- **`CanvasArea` をテストへ直接載せるには Provider が8つ要る**。
  `app_bootstrap.dart` の `buildAppProviders()` を使うのが早い
  （非同期なので `tester.runAsync` で呼ぶ）。
- **バックエンド（`backend/`、AWS CDK+Lambda+DynamoDB）はコード実装済み・
  未デプロイ**。DynamoDBの容量はAlways Free枠の25 RCU/25 WCUちょうどで、
  GSIを足すならどこかを減らす必要がある（`cdk synth` で検証される）。

## 6. やってはいけないこと

`CLAUDE.md` に事例つきで全部書いてある。**着手前に必ず読むこと。**
特に事故率が高いものだけ再掲する。

1. **`context.go()` を安易に使わない**。履歴を丸ごと置き換えるため、画面の
   奥（キャンバス編集中等）から使うと戻れなくなる。原則 `push()`。
2. **`XxxButton.styleFrom(textStyle:)` に素の `TextStyle()` を渡さない**。
   `ThemeData.fontFamily` すら継承されず端末標準フォントになる。
   `textTheme.labelLarge?.copyWith(...)` を土台にすること。
   `SnackBarThemeData.contentTextStyle` も同じ罠。
3. **ダイアログ内の `TextEditingController` を `showDialog().then()` で
   破棄しない**。`DisposeOnUnmount` ラッパーを使う（24箇所で実際に発生）。
4. **`Tooltip` で包んだボタンに外側から `onLongPress` を足しても発火しない**。
   `CanvasIconButton` の `longPressTooltip: false` を使う。
5. **タップを観測したいだけの親を `GestureDetector` で作らない**
   （ジェスチャーアリーナに参加してしまい、親子どちらかが必ず死ぬ）。
   `Listener` で見ること。
6. **`shouldRepaint` を1行で無効化しない**。`build()` で毎回新しい
   コレクションを渡すと、他の全項目に関係なく毎フレーム再描画される。
7. **`monetization_gate.dart` を一時的に書き換えたら必ず戻す**。
   過去に戻し忘れで、広告SDKとアプリ内課金が無条件に有効な状態が長く続いた。
8. **依存パッケージのバージョン固定には理由がある**。コメントを読まずに
   `flutter pub upgrade` しない。
9. **`flutter test` の既知の制約**：`path_provider` と `file_picker` は
   未登録。本物の非同期（`toImage`・`decodeImageFromPixels`・File I/O）は
   `tester.pump()` では進まず `tester.runAsync` が要る。

## 7. APKビルド（GitHub Actions）

`.github/workflows/build-apk.yml` は**手動実行のみ**（`workflow_dispatch`）で、
位置づけは**最終確認用**。細かな修正ごとに起動せず、対象テスト・
`flutter analyze`・必要な実キャプチャを先に済ませ、一連の追加修正が
すべて揃った最後に1回だけ起動すること。

- 同一ブランチで多重起動すると `concurrency`（`cancel-in-progress: true`）で
  古い実行が打ち切られる。
- `run_workflow` で `build-type` を省略すると既定値は **`debug`**（`release`
  ではない）。
- 生成物はArtifacts（保持1日）に加えGitHub Releaseへ上書き公開される。
  タグはビルド種別ごとに固定（`build-debug-latest` / `build-release-latest`）。
  **自分がどちらを起動したか必ず把握すること**（違う方を見て「古いままだ」と
  誤認する事故が起きやすい）。
- Releaseの `body` にビルド元コミットSHAが入っているのでそこで確認できる。

### R8（コード圧縮）について

過去に「実機起動直後クラッシュ」の原因をffmpeg関連と誤って結び付け一度全面
revertしたが、真因はリリースビルドのR8が2つのクラスを誤除去していたこと
だった。`android/app/proguard-rules.pro` へのkeepルール追加で修正済みで、
**この修正込みのR8有効ビルドが実機で正常動作することを確認済み**。
原因不明の実機クラッシュ（特に例外ハンドラーでも捕捉できないもの）に
遭遇したら、R8のusage.txt（ArtifactsにR8有効ビルドで残る）とAndroidの
「バグレポート」を早い段階で見ること。

## 9. ユーザーとのやり取りについて

- 依頼は日本語で来る。返答・コミットメッセージ・ドキュメントも日本語で書く。
- **相談せず最後まで進めて、完了後にまとめて報告する**ことを求められている。
  ただし「不具合を見つけたが直さずに報告だけする」のは求められていない。
  見つけたら直し、直したことを報告する。
- 仕様に穴があったら（例：「キャンセルボタンだけ」と指定されたが確定手段が
  無い）、**穴を埋めたうえでその判断を明示して報告する**。黙って仕様を
  変えないこと。
- ドキュメントは古くなったら**恐れずに書き換える**。`CLAUDE.md` 自体も
  更新対象。
