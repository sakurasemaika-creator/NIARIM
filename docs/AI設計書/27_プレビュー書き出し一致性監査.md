# プレビュー／書き出し一致性 現状監査・実装計画

監査対象: `dev_branch` の現行実装（2026-11-24確認）
目的: タイムラインで確認した映像・音声と、最終書き出しの結果を一致させる。

## 1. 現状確認で分かったこと

### 映像
- `ExportEngine.renderFrame()` は `LayerCompositor.composite()` を利用し、シーンのスタック／マスク、レイヤー・グループキーフレーム、カメラ変換、演出フィルターを適用してRGBAを生成する。
- `_TimelinePreviewState._rebuild()` も `LayerCompositor.composite()`、レイヤー／グループキーフレーム、カメラ変換、`FilterEngine.applyEffectFilters()` を利用している。したがって、合成・フィルターの主要部分は共有されている。
- ただし、現在のタイムラインプレビューはTileManagerのキャンバス幅・高さで描画し、その画像全体を表示する。一方、書き出しは `drawingWidth/drawingHeight` から `width/height` の中央範囲を切り出し、出力サイズで描画する。描画領域と書き出し領域が異なる場合、表示範囲・アスペクト比が一致しない可能性がある。
- ExportEngineは `scene != null` の場合に `stackFrameLayers(scene, frameIndex, layers)` を使用する。タイムラインプレビューは `ProjectService.stackedLayersOf()` を経由し、同じ `stackFrameLayers()` と `resolveFrameLayers()` を使っていることを確認した。したがって、現行ソース上のスタック／フレームマスク解決は共通関数であり、今後はこの共通関数自体の回帰テストと、実際の書き出し経路での検証を維持する。
- タイムライン上の動画素材は、静止画レイヤーの合成とは別に `VideoPlayerController` でライブ表示される。書き出しの動画素材デコード／合成経路と同一のフレーム評価ではない。

### 音声
- プレビューは `audioplayers` と `video_player` のプレイヤーをクリップ単位で管理する。
- プレビューの音声同期は `_currentFrame` と素材内フレーム位置を使い、音量とフェードを更新する。再生開始時の位置合わせと、再生中の継続的なクロック同期は別途検証が必要。
- 書き出しは `buildExportAudioPlan()` でシーン内の音声クリップ・動画内音声を抽出し、FFmpegで音量／フェード処理後にミックスする。
- したがって、現状は同じ音声評価器を共有していない。複数音声の同期、シーン境界、フェード曲線、動画内音声、読み上げの差異を回帰テストで検出する必要がある。

## 2. 一致性の定義

- 同一プロジェクトスナップショット、同一タイムスタンプ、同一出力設定で、プレビューのフレームと書き出しフレームの構図・クロップ・合成・色・エフェクトが一致する。
- 同一時刻のプレビュー音声と書き出し音声について、音源、開始時刻、速度、音量、フェード、ピッチ処理、ミックス結果が一致する。
- リアルタイムプレビューで処理が間に合わず画面更新が落ちることは許容する。ただし、時間評価・速度・エフェクトを変えて帳尻を合わせてはならない。停止・シーク後には指定時刻の正しいフレーム／音声を確認できる。
- エンコード形式やGPU/CPU演算の差による微小な数値誤差は、画像差・音声差の許容値を定義して自動テストする。

## 3. 推奨する実装順序

1. **TimelineRenderRequest / TimelineRenderResultを定義**し、プロジェクトスナップショット、シーン、グローバル時刻、出力範囲、サイズ、fpsを一つの要求にまとめる。
2. **共通フレーム評価器**へシーン／フレーム選択、stack・mask解決、レイヤー／グループキーフレーム、カメラ、エフェクト適用を集約する。プレビューとExportEngineの両方から呼ぶ。
3. **プレビューの出力範囲を統一**する。通常プレビューは書き出し設定に対応するフレームを表示し、書き出し範囲外を見せる編集用表示は「編集範囲表示」として明確に切り替える。
4. **共通音声タイムライン評価器**を作り、全クリップの開始・終了・素材内オフセット・速度・音量・フェード・ミュートを共通の時刻表にする。プレビュー用プレイヤーとFFmpegは同じ時刻表を入力として使う。
5. **動画素材の共通時刻評価**を導入し、プレビューと書き出しが同じ素材時刻を要求する。プレビューはデコード遅延に応じてフレームを落としてよいが、時刻を巻き戻したり倍率を変えたりしない。
6. **差分テスト**を追加する。プレビュー用と書き出し用に同じ時刻のフレーム／PCMを生成し、画像差、波形差、音量、開始・終了、AV同期を比較する。
7. 上記が成立してから速度変更・クロップ・分割などの新機能を両経路へ追加する。

## 4. 必須テストケース

- 描画キャンバスサイズと書き出しサイズが同じ／異なる（中央クロップ、縦横比違い）
- stack順、フレームマスク、ブレンドモード、グループ／レイヤーキーフレーム、カメラ、全演出フィルター
- シーン切替境界、先頭・末尾、キーフレーム境界、フレームレート変換
- 動画素材の使用開始／終了、音声の有無、動画内音声＋独立音声＋読み上げの同時再生
- 音量、フェードイン／アウト、クリップ重複、ミュート、素材欠損
- 速度0.1x、0.5x、1x、2x、16x、100x、端数倍率
- Undo/Redo・編集途中の変更・書き出し中の編集によるスナップショットの分離

## 5. この監査時点での結論

主要な静止画レイヤー合成と演出フィルターは既に共通エンジンを使っている。一方、書き出し範囲の適用、動画素材の表示、音声再生・ミックス、速度・クロップの時間評価はまだ完全な共通経路ではない。プレビュー／書き出し一致を「達成済み」と扱わず、上記の共通評価器と差分テストが実装・通過するまで未完了として管理する。

## 6. 追加実装：音声クリップのゲイン包絡線

監査後の段階的な改善として、`AudioClipEnvelope` を `lib/engine/export_audio.dart` に追加した。

- タイムラインプレビューの `_syncAudioClip()` と、FFmpeg書き出しの `exportAudioSourceArguments()` が同じ線形ゲイン／フェード境界の定義を参照する。
- フェードインとフェードアウトが重なる場合は、それぞれのゲインを乗算する。
- フェードアウト時間がクリップ全長を超える場合も、プレビューとFFmpegの傾きが一致するよう、基準音量と実効フェード時間を補正する。
- 通常フェード、重複フェード、書き出し上限で途中終了するクリップ、フェード時間がクリップより長いケースのテストを追加した。
- GitHub Actionsに対象テストと関連Dartファイルの解析を行う専用ワークフローを追加した。

この変更で共通化したのはクリップ単位の音量包絡線のみ。複数トラックのミキシング、動画音声と独立音声のクロック同期、読み上げ音声、速度変更、音声出力の実機比較は未完了である。CIと実機のテストが成功するまでは、この部分も検証済みと扱わない。

## 7. 追加実装：出力ビューポートの共通化

映像側の最初の差分として、中央クロップ位置の計算を `TimelineOutputViewport`（`lib/engine/timeline_output_viewport.dart`）へ集約した。

- ExportEngineとタイムラインプレビューは同じ描画領域／出力領域サイズから中央クロップのオフセットを求める。
- プレビューも書き出しと同じ出力幅・高さで画像を生成し、共通の `paintOutputViewport()` で中央クロップを描画した後、カメラ変換と演出フィルターを適用する。
- 背景色（不透明／半透明を含む）をフィルター前に出力領域へ描画し、プレビューと書き出しでフィルター対象の背景を揃える。
- カメラ変換の中心も出力領域の中心に統一する。
- 素材編集ギズモも出力領域のサイズとクロップ位置を考慮して表示・ドラッグ座標を計算する。
- 同サイズ、中央クロップ、奇数差分による小数オフセット、出力領域が描画領域より大きいケースの幾何テストに加え、テスト用画像を実際に描画して出力RGBAピクセルを比較するテストを追加し、専用CIで実行する。

このテストはクロップ幾何の一致を検証するもので、GPU合成結果のピクセル差分、全エフェクト、レイヤースタックの全組み合わせ、動画素材のデコードフレームまで一致したことを証明するものではない。実機での素材編集ギズモ操作と画像差分テストは引き続き必要である。

## 8. 動画素材のフレーム評価に関する追加監査

現行ソースを確認した結果、動画素材はまだプレビュー／書き出し共通の映像フレームとして合成されていない。

- 素材追加時、`_placeholderVideoFrame()` が動画の代表プレースホルダー画像を生成し、`LayerType.timelineVideo` のTileManagerピクセルとして保存する。
- タイムライン側の `_syncVideoClip()` は `VideoPlayerController` を初期化し、クリップの `useStart + elapsedFrames` に対応する時刻へseek／playする。ただし、現在のプレビュー画像生成は `LayerCompositor.composite()` にプレースホルダーを渡す経路で、デコード済み動画フレームを合成入力に差し込む処理は確認できない。
- 書き出し側の `ExportEngine.renderFrame()` もTileManagerのピクセルを合成するため、動画素材はプレースホルダー画像のままになる。書き出しフレームごとの動画デコード／合成処理は存在しない。
- したがって、動画素材については「プレビューと書き出しが一致している」のではなく、実動画フレームの反映自体が未実装の状態。動画の音声は別の再生・音声ミックス経路であり、映像フレームとは同期保証されていない。

### 次の実装方針

1. `materialId` から元動画ファイルを解決する責務をExportEngineへ直結させず、ProjectService／エクスポート要求側で `materialId -> file path + trim metadata` の不変な素材マップを組み立てて渡す。
2. タイムライン時刻からソース時刻を求める純粋関数（クリップ開始、sourceTrimStart、fps、速度、境界クランプ）を先に作り、単体テストする。
3. 動画デコーダーはフレーム単位でseek可能な共通インターフェースにし、プレビューはキャッシュ付き非同期取得、書き出しは決定的なオフライン取得を実装する。デコーダーのフレーム時刻／丸め規則を共通化する。
4. デコードした動画フレームをレイヤーの不透明度・マスク・変形・重なり順へ組み込み、カメラ／出力ビューポート／演出フィルターの共通経路へ流す。
5. 固定テスト動画から複数時刻のフレームを取得し、プレビュー経路と書き出し経路のRGBA差分を検証する。音声は別途PCMとAV同期テストを追加する。

この機能は現行のデータ供給契約を広げるため、動画素材の保存形式・素材参照・書き出し要求の受け渡しを確認せずにExportEngineへ直接FFmpegコマンドを追加しないこと。

## 9. 動画素材の共通ソース時刻マッピング（第一段階）

`TimelineVideoTimeMapper`（`lib/engine/timeline_video_time.dart`）を追加し、タイムライン上のフレームから素材内フレーム／プレイヤー時刻を求める純粋関数を切り出した。

- 入力はクリップ開始フレーム、クリップ長、素材内トリム開始・終了（終了は包含）、再生倍率、プロジェクトFPS。
- クリップ外の時刻、不正なFPS・倍率、逆転したトリム範囲は`null`として拒否する。
- 素材内フレーム位置は小数を保持し、トリム終端で包含範囲内にクランプした後、プレイヤー用ミリ秒へ丸める。
- 現在の動画プレビュー`_syncVideoClip()`はこのマッパーを使用する。現時点では既存挙動に合わせて再生倍率1.0、プロジェクトFPSを素材フレーム番号の時間基準としている。
- クリップ範囲、トリム、端数倍率、終端クランプ、範囲外、不正入力、ミリ秒丸めを単体テストし、専用CIに追加した。

**未実装／未検証:** 再生速度UI・永続モデルへの接続、素材固有FPS／可変フレームレートの扱い、プレビューの連続再生クロック補正、デコード済みフレームのレイヤー合成、ExportEngineへの動画フレーム供給はまだない。今回の変更は時刻計算の共通化までであり、動画の実映像が書き出されるようになったわけではない。

次段階では`MaterialService`が保持する素材ID・`Materials/`内ファイル・`MaterialAsset.duration`をエクスポート要求へ不変スナップショットとして渡す設計を確認し、動画デコーダーのプレビュー／オフライン共通インターフェースを作る。素材FPSを取得できる場合は、プロジェクトFPSと素材FPSを明示的に分離する。

## 10. 素材ファイルの受け渡しとレイヤー合成の接続点

前節の次段階を実装する前に、素材ファイルの保存・解決と合成器の実際の呼び出し境界を追加確認した。

- `MaterialService` はプロジェクトの `Materials/` 配下へ `MaterialAsset.storageName`（素材ID＋元拡張子）で保存し、`pathOf(projectId, materialId)` で実ファイルパスを解決する。メタデータには現在、幅・高さ・durationはあるが、素材固有FPS／フレームレートの情報はない。
- 書き出し画面（`lib/screens/export/export_screen.dart`）は `buildExportAudioPlan()` に `MaterialService.pathOf` を渡して音声素材を解決している。一方、動画映像用の素材マップは構築せず、`ExportEngine.exportMp4()` にも渡していない。
- プレビューの `_TrackClip` は `filePath` を保持し、`VideoPlayerController.file` で再生する。しかし、このコントローラーの映像テクスチャは `LayerCompositor` の入力には接続されていない。
- `LayerCompositor._drawLayer()` は各レイヤー画像を常に `TileManager.compositeLayerToImage(keyOf(layer))` から取得する。したがって、動画デコード画像を正しく挿入するには、TileManagerの保存ピクセルを動画フレームで上書きするのではなく、レイヤーID／時刻に応じた画像供給コールバック（または同等の明示的な画像ソース契約）を合成器へ追加するのが適切である。
- その画像供給契約は通常レイヤーと同じく、不透明度、ブレンド、マスク、クリッピング、レイヤー／グループ変形、重なり順を通る必要がある。CPUブレンド用の孤立レイヤー描画経路にも同じ画像ソースを渡さなければ、ブレンドモードによって動画レイヤーだけ別の結果になる。

### 実装順序の更新

1. `MaterialService` から、動画素材ID・実ファイルパス・duration・将来の素材FPS情報を含む不変スナップショットを作り、書き出し要求へ渡す。欠損ファイルは空扱いにせず、明示的な欠損状態として保持する。
2. `LayerCompositor` に、レイヤーIDと評価時刻を入力として画像を供給する任意のresolver契約を追加する。通常レイヤーは従来どおりTileManagerへフォールバックし、動画レイヤーのみデコード画像を使う。画像の所有権・dispose責務・非同期キャンセルをAPIで明確にする。
3. フレーム時刻評価器とseek可能なデコーダーを分離する。プレビューとオフライン書き出しは同じ時刻評価／フレーム選択規則を使い、デコード実装だけをリアルタイム／決定的オフライン用途に分ける。
4. プレビューとMP4/GIF/WebM/AVIの各フレーム生成経路へ同じresolver契約を接続する。未接続の形式を動画対応済みと表示しない。
5. 動画なし／1本／複数本、重なり、マスク、クリッピング、キーフレーム、カメラ、シーク、トリム終端、欠損素材を含むRGBA比較を追加する。

**現時点での実装状態:** 素材IDからファイルパスを解決する既存APIと、合成器がTileManager画像に固定されている箇所を特定した段階。動画素材スナップショット、resolver、デコーダー、動画フレーム合成はいずれもまだ実装していない。

## 11. 動画素材スナップショット（第二段階）

`VideoMaterialSnapshot`（`lib/engine/video_material_snapshot.dart`）と`MaterialService.videoSnapshotOf(projectId)`を追加した。

- プロジェクト内に登録された動画素材だけを対象に、素材ID・実ファイルパス・既知のdurationを読み取り専用のスナップショットへまとめる。
- スナップショットは不変Mapとして保持し、エクスポート開始後に素材一覧が変更されても、そのジョブが参照する素材情報を固定できる土台にした。
- 登録済み素材の実ファイルが欠損している場合も素材IDを残し、パスをnull／`isMissing`として明示する。欠損素材をTileManagerのプレースホルダー画像で正常素材のように扱わないための契約である。
- 画像・音声素材は動画スナップショットに混入させない。
- 純粋モデルのテストで、動画のみの抽出、パス・duration保持、欠損表現、Mapの不変性を検証する。専用CIにテストと対象ファイルの静的解析を追加した。

**まだ未接続:** `ExportScreen`／`ExportEngine`へのスナップショット引き渡し、タイムラインプレビューへの引き渡し、デコーダー、`LayerCompositor`画像resolver、実動画フレームの合成は未実装。したがって、この段階で動画のプレビュー／書き出しが改善したとは扱わない。次はスナップショットをexport jobへ固定して渡す入口を作り、続いて画像resolverを合成器の通常・CPUブレンド両経路へ通す。

## 12. 動画フレーム取得基盤（第2段階）

動画素材の実フレームを、プレビューと書き出しの両方へ同じ規則で供給するための基盤を追加した。**この段階ではまだレイヤー合成・プレビュー・書き出しのいずれにも接続していない。** 画面上・書き出し結果の動画は、引き続きプレースホルダー画像のままである。

### 実装済み

- `VideoFrameTimeline`（`lib/engine/video_frame_timeline.dart`）
  - FFprobeで取得したパケットの表示時刻（PTS）表を、コンテナ開始時刻（FFmpegの`-ss`の基準）からのマイクロ秒で保持する。編集リストで破棄されるパケット（flagsに`D`）、PTSなし、負の時刻は除外する。
  - **フレーム選択規則（プレビュー・書き出し共通）**：時刻`t`で表示されるフレームは「PTSが`t + 0.5ms`以下となる最後のフレーム」。最初のフレームより前は先頭フレーム、最後のフレーム以降は最終フレームを保持する。0.5msの許容は、ミリ秒単位の時間軸を持つコンテナと、プロジェクトFPSからマイクロ秒への変換の丸めを吸収するためのもの（240fpsでもフレーム間隔は約4.2ms）。
  - FPSに依存しないため、可変フレームレート動画やFPSが取得できない動画でも同じ規則で選択できる。素材FPSはメタデータとして保存していない（推測値を正しい値として保存しない方針）。
  - 回転メタデータ（side data／旧`rotate`タグ）を考慮した表示サイズを参考情報として保持する。
- `TimelineVideoTimeMapper.sourceTimeAt()`：フレーム選択用に、ミリ秒へ丸めずマイクロ秒精度で素材時刻を返す。既存の`sourcePositionAt()`（プレイヤーのシーク用、ミリ秒）は変更していない。
- `FfmpegVideoFrameDecoder`（`lib/engine/video_frame_decoder.dart`）
  - 端末ではFFmpegKit、テストではシステムのffmpeg/ffprobeで、**同一の引数リスト**を実行する。
  - 実測の結果、FFmpegの入力側シーク（`-ss t`）は「t以上で最初のフレーム」を返し、最終フレームの表示区間内では何も返さない。これは表示中のフレームと一致しないため、フレーム番号はDart側で上記規則により決め、FFmpegには直前フレームとの中点時刻でシークさせる。
  - 出力は、要求サイズ（通常はキャンバスサイズ）に縦横比を維持して収め、中央配置し、余白を透明黒で埋めたRGBA。回転はFFmpegの自動回転で適用する。画像素材をキャンバスへラスタライズする配置と同じ考え方で、既存のレイヤー変形・マスク・クリッピングにそのまま渡せる形にした。
  - 拡大縮小フラグを`bicubic+accurate_rnd+full_chroma_int+bitexact`に固定し、プレビューと書き出しで同一にする。
  - 一時ファイルはコマンドごとに作業ディレクトリへ書き、読み込み後（失敗時も）削除する。
- `VideoFrameProvider`（`lib/engine/video_frame_provider.dart`）
  - 素材ファイルは開始時に取得した`VideoMaterialSnapshot`からのみ解決する。
  - 結果は`VideoFrameReady`（画像の所有権は呼び出し側。必ずdisposeする）か`VideoFrameUnavailable`（理由付き）。素材なし・ファイル欠損・読み取り不可・デコード失敗は「失敗」として区別し、代替画像を返さない。
  - 同じフレームに対応する時刻は1回のデコードを共有する。同時要求も1回のデコードにまとめ、各呼び出し側へ別の画像ハンドルを渡す。
  - バイト数上限付きLRUキャッシュ（既定96MB）。キャッシュから追い出しても、既に返した画像は無効にならない。
  - 同時デコード数を制限する（既定2）。
  - 同じキー（例：プレビューの1レイヤー）を持つ要求は「最新優先」。古い要求は`superseded`となり、まだデコード待ちなら実際にはデコードしない（スクラブ時のデコード過多を防ぐ）。
  - キャンセル判定（書き出しのキャンセルトークン等）と`dispose()`に対応。破棄後に完了したデコード結果はキャッシュせず解放する。

### 未検証・制約

- **Android実機（FFmpegKit）での動作は未確認。** 端末のFFmpegKitに含まれるFFmpegのバージョン・最適化は、CIのFFmpeg 6.1と異なる。`bitexact`等を指定しているが、端末とCIの間でRGBAが完全一致するかは未検証で、許容誤差もまだ定義していない（プレビューと書き出しは同じ端末上で同じデコーダーを使うため、その間の一致はこの差の影響を受けない）。
