## タイムライン再生中に画面全体が毎フレーム再ビルドされる（対応済み）

`_currentFrame`を`ValueNotifier`化して解消した。詳細は
`12_実装チェックリスト.md`の「タイムライン再生中の全画面再ビルドを解消」の
節を参照。以下は着手前に書いた記録（判断の経緯として残す）。



### 現象と原因

`_TimelineScreenState`の再生タイマーは、プロジェクトのfps間隔
（24fpsなら約41ms）で

```dart
setState(() { _currentFrame = (_currentFrame + 1) % total; });
```

を呼ぶ。`_currentFrame`は`_TimelineScreenState`のフィールドなので、
この`setState`は**8,000行規模のタイムライン画面のウィジェットツリー全体**
（フレーム一覧・各トラック・シーンタブ・ツールバー・プレビュー）を毎秒
24〜60回作り直す。実際に更新が要るのはプレビュー画像と再生位置の
ハイライトだけ。

同じ理由で、`_buildXxx()`系の各メソッドにある`context.watch<ProjectService>()`
（15箇所）も、すべて同じStateのcontextを使うため画面全体が購読者になる。
ただしProjectServiceは描画のたびには通知しない
（`pingWorkActivity()`は通知しない、`markLineartDirty()`はフラグが
立っていない時だけ通知する）ため、こちらは毎フレームのコストではない。

### 提案する直し方

`_currentFrame`を`ValueNotifier<int>`にし、再生位置に追従する必要がある
箇所（プレビュー・再生ヘッド・フレーム一覧のハイライト）だけを
`ValueListenableBuilder`で包む。`_currentFrame`は互換のためgetterとして
残し、書き込みはnotifier経由にする。

### 着手前に判断が要る点

- `_currentFrame`の参照が同ファイル内に49箇所あり、どれが「再生に追従
  すべき」でどれが「操作時にだけ更新されればよい」かの切り分けが要る。
  機械的な置換はできない。
- 効果（何ms速くなるか）も、崩れないか（再生・スクラブ・フレーム移動
  モードの挙動）も、**実機でしか確認できない**。この開発環境には実機が
  無いため、変更しても「たぶん速い・たぶん壊れていない」以上のことが
  言えない。
- 上流が並行して同ファイルを編集しているため、大きな差分はコンフリクト
  しやすい。

着手前は「実機で確認できる状況になってから」と判断していたが、49箇所を
読んで分類し、ウィジェットテストで挙動と再ビルド範囲の両方を検証できた
ため対応した。

### 今回入れた部分的な対応

再生中のフレーム一覧の中央寄せだけは`jumpTo`にした。従来は200msの
`animateTo`を毎フレーム張り直しており、前のアニメーションを打ち切って
新しいSimulationを作る動作を毎秒24回繰り返していた。処理が無駄なうえ、
スクロールが再生位置に追いつかず遅れて揺れる状態だった。
