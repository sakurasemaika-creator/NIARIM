# 13B クリエイターミッションとコイン報酬仕様（v2・2026-11-04）

> **13Aの追加仕様。** 価格比較の単位は「1円相当＝100コイン」、任意のAdMobリワード広告は初期10コイン/検証済み視聴。無償コインは購入・現金化・譲渡できない。制作・作品広場での「ミッション」について、ここを正とする。前版の「全17種類・生涯合計5,930コイン、作品別もアカウント1回限り」の設計は廃止。

## 1. ユーザーによる確定した仕様

1. **アカウント1回限りの階段式達成ミッション**：制作時間は**10万時間**まで、NIARIM内のフォロワーは**100万人**まで、条件以上のブックマークを持つ公開作品数は**1万作品**まで。上位条件を満たしても下位を後から獲得でき、ミッションごとに生涯1回。コイン残高・達成履歴はGoogleログインに紐づくNIARIM User IDで引き継ぐ。
2. **作品ごとに1回限り**：1作品のNIARIM内ブックマーク数とNIARIM独自のブックマークランキングの各達成段階は**各作品ごとに1回ずつ**。作品Aで獲得しても作品Bで改めて獲得できる。一方、同じ作品の非公開化→再公開、別端末での再実行、再ランクインでは同じ段階を二重発行しない。削除済み作品の報酬履歴も消さない。
3. **50時間ボーナス**：サーバー検証済み累計制作時間**50時間に到達した時点で55,000コイン**を追加付与（アカウント生涯1回）。価格比較の月額550円×100コインという**仮の1か月フルPremium価格55,000コイン**をカバーする量。50時間以前のミッション報酬を合算するとさらに上回る。実際の交換価格は未確定のため、「50時間で必ず1か月無料」と正式表示する前に、本番価格との整合性を必ず確認。正式価格が55,000コインを超える場合、50時間報酬の増額または1か月の特別交換権の追加が必要。
4. **ランキング難易度の変化**：NIARIM内で公開中の対象作品が増えると、順位上位の報酬額も増える。報酬はユーザーに提示した段階で固定し、後の倍率変化・広告単価変化で減らさない。ここでいう「ランキング」は**NIARIM独自のブックマーク数ランキングだけ**であり、YouTube再生数・高評価・登録者数やそれらを含む総合ランキングではない。

|---|---:|---:|---:|---:|
| 初期基本報酬 | 100 | 300 | 600 | 1,000 |

**公開作品数に応じた倍率**：

- 公開中対象作品1〜999件：基本報酬×1
- 1,000〜9,999件：×2
- 10,000〜99,999件：×3
- 100,000〜999,999件：×4
- 1,000,000件以上：×5

**例**：作品総数が1万件になったあとに作品Aが1位になれば1,000×3＝**3,000コイン**。作品Bも別に1位を達成すれば同様に付与。作品Aが再び1位になっても同じランク段階の再付与なし。

実際の倍率の判断は既存の統計バッチが処理した**公開中作品の集計値**から行い、ランキングを表示する度に全作品を読み直さない。ランキングの掲載期間や同数順位のタイブレークが変わる場合はサーバーが一律に判定する。

作品ごとの報酬にアカウント合計の固定上限は設けない。したがって**旧仕様の「生涯最大5,930コイン」は完全撤廃**。アカウント共通報酬上限と、1作品あたりの報酬上限、運営全体の将来債務を混同しない。

## 3. 制作時間は「端末表示用」と「報酬審査用」を分離

現行 `ProjectService` は描画・タイムライン画面で10秒ごとに加算し、無操作1分で停止する。これは作品詳細画面の `totalWorkSeconds` に利用し続ける。しかし端末内データは自由に変更可能で、スクラブなど非制作操作も操作扱いになるため、50時間＝55,000コインの証明には使用不可。

### 個人開発向けの低コスト検証案

- Google認証済みNIARIM IDに対してサーバーが編集セッションID・開始時刻・最終確認時刻を発行し、1アカウントの同時セッションを原則1件に制限。
- 10〜15分ごと、または編集画面を離れる時にのみ、単調増加シーケンス・編集実変更イベントの**件数のみ**・候補経過秒数を送信する。ペンの軌跡・画像・素材・座標や大量の操作履歴は保存しない。端末でオフライン編集しても作品は保持し、報酬用の時間は後で再検証する。
- サーバーはサーバー時計の時間差・日次上限・1セッション最大許容秒数・シーケンス重複・同時セッション・短時間に多すぎる操作・アカウント不正リスクで上限を設け、確認した時間だけ1ユーザーの整数 `verifiedEditSeconds` を加算する。
- 改ざんアプリやマクロはイベントを偽装できるため、完全な不正防止にはならない。高額な50時間達成時など価値の高い操作だけにPlay Integrityや保留・監査を利用する。Play Integrityの既定上限は**10,000リクエスト/日**なので全ての15分更新に使わない。
- DynamoDBにはアカウントごとの**累計時間と短いセッション状態だけ**を更新する。秒ごとの書き込み、動画や画像アップロード、操作座標ログ、外部の高額な不正検知サービスは導入しない。
- **このセッション検証APIとクライアント送信は未実装で、制作時間ミッションは本番報酬受け取り不可のまま。** 計測が検証できるまでは55,000コインを発行しない。

### 想定する運用量と費用

| 前提 | 15分単位の制作時間同期数 |
|---|---:|
| 1,000人 × 1人あたり月20時間 | 約80,000回/月 |
| 10,000人 × 1人あたり月20時間 | 約800,000回/月 |

Lambdaの無料枠（一般に月100万件のリクエストと40万GB秒）やDynamoDBのProvisioned 25WCU/25RCU・25GB枠を利用できる規模がある。ただし**既存サービスの合算、1KB超のアイテム、トランザクション、バースト、GSI、CloudWatch Logs、認証処理、ネットワーク転送**は別途考慮する。無料枠以内でも短時間の集中でスロットリングするため、送信時刻を端末ごとに分散し、ジッター・指数バックオフを実装する。料金計測とAWS Budgetsアラートを設定してからONにする。

## 4. DynamoDBの最小構成と二重付与防止

すべて既存の単一DynamoDBテーブル、**GSI追加なし**。

- `USER#{id}/MISSION_STATE_V1`：ユーザー単位の39段階の獲得済み`claimedMask`（整数1個）・整数の累計検証済み制作秒数・集計の整合性番号`revision`・必要な達成日時の数値マップ・保留報酬額だけ。
- `USER#{id}/MISSION_WORK#{workId}`：**当該作品に報酬が発生した場合のみ**追加する小さな記録。ブックマーク／ランク14段階のビットマスクと時刻マップを保持。公開作品ごとに無条件で巨大な履歴を保存しない。作品削除後も不正な重複受給防止のため記録は残す（アカウント削除時はプライバシー規則に従い適切に削除）。
- `USER#{id}/COIN_WALLET`：既存ウォレットに無料ミッション獲得コインを加算。ミッション状態の獲得ビットの条件付き更新とウォレットへの加算を**1トランザクション**にし、二重クリック・別端末・通信再試行で二重付与させない。
- 受取条件の検証は既存サーバーのNIARIMブックマークとフォロワー数、本人の公開作品のみ。SNS・YouTubeの再生数・高評価・登録者数などのYouTube指標に連動する報酬は作らない。
- 高額な達成報酬の前に**48時間の条件持続確認**と追加の不正リスク対策が必要。48時間待つだけでは複数Googleアカウント／架空作品の水増しを防げず、Play Integrityやアカウント年齢・異常判定などを準備する。
- 単一アカウントの報酬計算時、1万作品すべてを毎回読むのは不可。現在のサーバーの`qualifiedWorks`計算は**最大500作品までの段階的読み出し**で、超過すると保留状態にする。大量作品の段階には、既存インデックスからのページ継続検証、または既存ブックマーク更新で増減する小さな集約カウンターの導入が必要。現時点で「1万作品の検証が完成した」と称しない。
- 作品個別クエリは`GET /me/missions?workId=動画ID`でその作品だけのビットマスクを取得する。指定なしでは作品別の獲得済み状態を誤って「アカウント全体の未獲得」と表示しない。
- `claimedMask` は最大53ビットの安全な整数。登録済みIDやbitは再配置せず、次の拡張では`MISSION_STATE_V2`や`mask2`等で分割。表示の翻訳・ミッション内容はアプリのコードで復元し、各ユーザーのレコードに重複保存しない。

## 5. 収益・コンプライアンスの考え方

50時間のボーナスは「利用習慣形成・継続率向上・魅力的な作品・紹介流入」のための**マーケティング投資**。広告収益を経由しないコインを発行する以上、1ユーザーごとの交換時純利益がサブスク以上になる保証は成立しない。50時間で55,000コインの大半を広告視聴せず得た人は、広告の単発収益だけでは対応できない。代わりに週次・月次の継続率、投稿者率、閲覧者流入、広告収益、Premium移行率、発行済みコイン債務の推移で施策を評価する。自動付与を無制限に広げない。

**YouTube API Services Developer Policies**：視聴・高評価・シェア・登録・コメント等のYouTube行為へ報酬を提供しない。NIARIM内の独立したブックマークをYouTubeの「いいね」と混同させない。<https://developers.google.com/youtube/terms/developer-policies>

## 7. 2026-11-04 制作時間の低負荷サーバー計測パイロット（追加実装）

- バックエンド `POST /me/missions/edit-session` を追加。これは報酬を発行しない**計測試験用API**で、既定では `CREATOR_EDIT_SESSION_PILOT_ENABLED` が未設定のため、403 `EDIT_SESSION_PILOT_DISABLED` を返す。CDKデプロイを行ったわけではない。
- `{"action":"start","startNonce":"UUID"}` で、認証済みNIARIMユーザーに短命セッションIDを発行。クライアント生成のUUIDは再送の重複開始防止にのみ使い、端末からユーザーIDを指定できない。別端末の未期限切れセッションは重複開始を拒否。
- `{"action":"checkpoint","sessionId":"UUID","sequence":1,"activeSeconds":900,"meaningfulMutations":10,"stop":false}` は15分間隔程度で送る。値は例であり、**実際の有効秒数はサーバーの現在時刻−前回受信時刻を超えられない**。20分より長い未通信間隔は期限切れ。1区間最大900秒、実変更イベント1件あたりの計上上限90秒、実変更イベント2件未満なら0秒、UTC基準で1日最大8時間の候補記録。
- `stop:true` でセッション終了。シーケンス番号とDynamoDB条件付き書き込みで競合と多重計上を防止。通信が成功したのに応答だけ失われた終了要求には、最後の小さな終了レシートを返す。
- 保存先は既存 `USER#{id}/MISSION_STATE_V1` だけ：`candidateEditSeconds`、`editDailyCandidateSeconds`、`editDay`、小さな`editSession`、`lastEditStop`など。筆跡・画像・動画・パス・編集操作履歴は送信・保存しない。1回のチェックポイントに**強整合性読取1回＋条件付き書込最大1回**。追加テーブル・GSI・秒単位のアップロードなし。
- この候補時間は**`verifiedEditSeconds`にも`COIN_WALLET`にも一切加算しない**。アプリ内には「サーバー集計の候補（審査前）」と表示する。認証、サーバー時計や操作数だけでは真の編集を証明できないため、実際の50時間報酬55,000コインを発行する前にPlay Integrity/不正行為監査/モデレーションを連結すること。
- Flutter `CommunityApi.beginCreatorEditSession` / `checkpointCreatorEditSession` のAPI呼び出しを追加。ただしキャンバス/タイムラインの**実編集確定イベントの収集・自動チェックポイント送信はまだ未配線**。いまはパイロットAPIを本番有効化しないこと。既存の画面表示用 `Project.totalWorkSeconds` は変更していない。
- バックエンドの `backend-ci.yml` で型チェック・Vitest・CDK synthまで検証する。AWSへのデプロイ、UIの端末実測、Play Integrity連携は別途必要。

## 8. 低コストの継続運用と検証の優先順位

1. まずサーバー側の不正判定を完成させ、クライアントは単なるタップ・再生・スクラブと**実際に保存される編集変更**を区別する。
2. 制作時間の集計は10〜15分間隔と画面退出時に限定。端末オフライン中の長時間をサーバーが無条件で認めない一方、描画自体はオフラインでも続行できる。
3. 作品数1万件の複数作品ミッションは現在の安全な500作品上限で一度に検証できない。事前集計または継続可能なページ走査を実装するまで、高段階を払い出さない。
4. 作品別のブックマーク・ランキング履歴を作品ごとに復元し、`/creator-missions?workId=...` の画面導線と本人のみの参照を維持する。一般の一覧では作品別の既得状態を1件だけの状態と混同しない。
5. 50時間の大きな無償報酬は利用定着のための広告宣伝費として管理し、ユーザー数・有料転換率・残高の未使用分と交換コストの推移を確認する。
