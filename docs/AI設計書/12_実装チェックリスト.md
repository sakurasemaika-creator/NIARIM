## パフォーマンス

      ユーザーの指示で安全な設計に作り直して対応した）：
      TileManagerに`compositeLayerToImage()`の合成結果（レイヤー1枚分のui.Image）を
      layerIdごとにキャッシュするLRU方式のキャッシュ（上限16件、超過分は最も古い
      ものから破棄）を追加した。オブジェクトidentityやハッシュ比較には頼らず、
      `_tiles`を変更する全メソッド（getOrCreateTile・replaceLayerPixels・copyLayer・
      renameKey・removeLayer・removeSceneTiles・applyTileSnapshot・importAll）の
      内部で明示的にキャッシュを無効化する設計とし、外部から呼ばれる`markDirty`
      （一部の描画パスでしか呼ばれず信頼できない）には依存しない。呼び出し元が
      返された画像を自由にdispose()できるよう、キャッシュ本体ではなく
      `ui.Image.clone()`（ネイティブ側で参照カウントされるハンドル）を返すため、
      複数箇所が同じレイヤーを同時に参照してもdispose済み画像の再利用は起きない。
      **（2026-08-07 追記・Task#75）** `test/tile_manager_test.dart`を新設し、
      「キャッシュヒット時にdispose済み画像を再利用しないか」「各種変更操作
      （getOrCreateTile書き込み・replaceLayerPixels・renameKey・removeLayer・
      applyTileSnapshot・importAll）後に古いキャッシュを返さず正しく再合成
      されるか」「LRU上限を超える件数のレイヤーを合成してもクラッシュしないか」
      を実際にTileManagerを動かして機械的に検証した（`flutter test`で全件PASS）。
      実機での目視確認は依然できないが、キャッシュの正しさそのものは机上の
      レビューだけでなく実行結果で裏付けられている。

`GeneratedPluginRegistrant`は除去0件（正常）だった。

全体でも小規模なため、個別の除去パターンを追いかけるのではなく丸ごと
keepすることで同種の問題の再発も防ぐ）。`android/app/build.gradle.kts`
のコメントも通常の説明へ戻した（R8は引き続き有効のまま）。

**現状**：この修正込みでのR8有効ビルドの実機起動確認はまだ完了して
いない。次のビルドでusage.txtに`com.niarim.niarim`が再び現れない

### 追記：R8起動時クラッシュの真の原因を実機バグレポートで特定（WorkManager/Room）

背景：診断用クラッシュ画面（Kotlin側の例外ハンドラー）でも捕捉できない
クラッシュが継続したため、ユーザーにAndroidの「バグレポート」機能
（設定 → 開発者向けオプション → バグレポートを取得）でシステムログ
一式を取得してもらい、`FATAL EXCEPTION`・`Process com.niarim.niarim`
等のキーワードで該当箇所を特定してもらった。

実機ログから、起動直後（アプリプロセスがTOP＝フォアグラウンドの状態）に
以下の例外で確実にクラッシュしていることが判明した。
```
java.lang.RuntimeException: Unable to get provider
androidx.startup.InitializationProvider:
com.google.android.gms.internal.ads.kc: java.lang.RuntimeException:
Failed to create an instance of androidx.work.impl.WorkDatabase
```

原因：`google_mobile_ads`（広告SDK）が内部でバックグラウンド処理に
WorkManagerを使用しており、そのWorkManagerが内部で使うRoom生成の
データベース実装クラス（`WorkDatabase`の実装）が、R8の最適化
（`proguard-android-optimize.txt`使用によるアグレッシブなクラス
マージ等）で壊れてWorkManagerの初期化に失敗していた。この初期化は
`androidx.startup.InitializationProvider`という**ContentProvider**
経由で、`Application.onCreate()`より前（`ActivityThread.
handleBindApplication()`内の`installContentProviders()`時点）に
実行されるため、通常の未捕捉例外ハンドラー（`MainApplication.kt`で
登録した診断用のもの含む）では原理的に捕捉できないタイミングだった。
これが、診断用クラッシュ画面が一度も表示されなかった理由でもある。

このバグは今回のMediaCodec化・ffmpeg-kitパッケージ変更とは無関係で、
google_mobile_ads導入時（本セッションよりずっと以前）からR8有効の
リリースビルドで常に発生していた可能性が高い。これまでの一連の
revertはいずれも症状を変えなかったのはこのため。

対応：`android/app/proguard-rules.pro`へ以下を追加。
```
-keep class androidx.work.** { *; }
-keep class * extends androidx.room.RoomDatabase
-keep class androidx.startup.** { *; }
-dontwarn androidx.work.**
```

**現状**：この修正込みでの実機起動確認はまだ。診断用クラッシュ画面
（MainApplication.kt・CrashActivity.kt）は今回の原因特定には直接
貢献しなかった（例外発生タイミングが早すぎたため）が、今後別の問題が
発生した際の保険として、実機での起動成功が確認できるまでは一旦残す。

**実機検証結果：修正版をユーザーが実機に再インストールし（初回は
インストール自体が一時的に失敗したが再試行で成功）、正常に起動する
ことを確認済み。R8有効ビルドの起動時クラッシュは、WorkManager/Room
のkeepルール追加により完全に解消した。**

### 追記：#89 タッチ操作での描画が一切できない重大バグを修正

原因：`canvas_area.dart`の`_onPointerDown`/`_onPointerMove`/`_onPointerUp`に
`if (type == InputType.touch) return;`という無条件ガードが、ペン・
バケツ・投げ縄・トーン/スタンプサブツールなど、ほぼ全ての描画操作の
入口に存在していた。これによりスタイラス・マウス以外（＝指のタッチ）
からの入力は常に無視され、スマホでの指描画が完全に機能しない状態
だった。一方`InputHandler`には本来パームリジェクション（スタイラス
使用中の誤タッチ無視）用と思われる`shouldDraw(event, {hasStylusSupport})`
というメソッドが用意されていたが、実際にはどこからも呼ばれておらず
死んでいた。

対応：全ての無条件タッチブロックを`type == InputType.touch &&
_inputHandler.isStylusActive`という条件へ変更。これにより
- スタイラス非使用時（タッチのみの端末、あるいはスタイラス保有端末で
  指を使っている場合）は通常通りタッチで描画できる
- スタイラスで描画中に手のひらが触れた場合のみ、そのタッチは無視される
  （本来の意図通りのパームリジェクション）
という挙動になる。あわせて、バケツ/投げ縄/トーン/スタンプの
Up側ハンドラーでの`_inputHandler.onStylusUp()`呼び出しが
`if (type == InputType.touch)`条件付き（＝スタイラスの指Upではなく
タッチのUpでしか呼ばれない、逆の条件になっていた）だったため、
スタイラスでこれらのツールを使い終えた後に`isStylusActive`が
解除されずスタックする不具合も合わせて修正（ポインター種別を問わず
Up時に呼ぶよう変更）。また、既定の直線ストローク用Upハンドラー内の
`if (type == InputType.touch) { onStylusUp(); return; }`も同様の
条件不備により、タッチで描いたストロークが`_drawingEngine.endStroke()`
まで到達せず正しく確定されない状態だったため、こちらもパームリジェクト
時のみ早期returnするよう修正。

未対応（今回のスコープ外、今後のラウンドで対応）：二本指回転・

- 選択範囲の中をタップ：移動（ドラッグした分だけ平行移動）
- 選択範囲右下の丸ハンドル：拡大縮小（中心基準）
- 選択範囲上部の丸ハンドル：回転（中心基準）
- 選択範囲の外をタップ：従来通り新規選択の開始（既存選択は破棄）

移動・拡大縮小・回転する別のツール）と同じ操作感で、内部の行列計算
ロジック（`_computeTransformMatrix`）も共通化した。ただし変形ツールは
レイヤー全体を対象にするのに対し、こちらは選択マスクで切り取った
範囲のみを対象にする点が異なる。

**実装方式**：操作開始時に、現在レイヤーの合成画像を選択マスクで
切り取った「浮動画像」を生成し、同時に元レイヤーの選択範囲内を透明化

空いた状態）の上に変形後の浮動画像を合成して1枚に書き戻し、選択マスク
自体にも同じ変形をかけて選択範囲を新しい位置へ追従させる（続けて
同じ選択範囲を再度移動・変形できるようにするため）。

**データ消失の防止**：浮動画像の生成は非同期（合成画像のデコード待ち）
のため、生成が完了する前に指を離した場合に「元レイヤーの切り取りだけが
残り、貼り戻す浮動画像が無い」という消失が起き得た。切り取り処理の
直前に操作がまだアクティブかどうかを再チェックすることで、この場合は
切り取り自体を行わないようにして防いだ。

**既知の制約（今回のスコープ外）**：ごく短時間に連続して選択の変形操作
