# 29_動画投稿・ランキング機能仕様

バックエンド（YouTube投稿・DynamoDB・ランキング集計）は仕様検討段階で
あり、コード実装には未着手。AWS・Google Cloud側のアカウント整備、OAuth
審査など、このリポジトリの外側の前提条件が整ってから着手する。本章の
内容は複数回のレビューを経た確定仕様。ただし検索・タグ機能・フローティング
プレビュー・NIARIM側公開/非公開設定など、バックエンドを介さずUI・
アプリ内状態のみで確認できる一部の挙動は、ダミーデータへのクライアント
側実装として先行してコード実装済み（詳細は19章の対応状況まとめを参照）。

## 1. 基本方針

NIARIMは作品動画そのものを自前で保存・配信しない。動画のホスティング先は
YouTubeに限定し、NIARIM側は動画のメタデータのみを保持する。

```text
NIARIM → YouTubeへ動画投稿 → YouTube上に動画を保存・配信
NIARIMには動画のメタデータ（動画ID・再生数等）だけ保存
```

ニコニコ動画・TikTok等、YouTube以外への投稿選択肢は対象外とする（再生数・
高評価数・コメント数の取得元をYouTube 1本に統一し、ランキング計算を単純化
するため）。

NIARIMは「短時間で大量の動画を投稿するSNS」ではなく、**アニメーションを
制作して完成した作品を公開するアプリ**である。この性質が11章の投稿上限
方針の前提になる。

## 2. ログイン要否

「アニメを描いて遊ぶだけ」のユーザーにログインを要求しない一方、他の
ユーザーを識別する必要がある操作（投稿・通報・ブロック）だけGoogle認証を
要求する。

| 機能 | ログイン |
|------|---------|
| アニメ制作・端末内保存 | 不要 |
| みんなの作品を見る／新着／ランキング | 不要 |
| 作者の作品一覧を見る | 不要 |
| YouTube投稿 | **必須** |
| 作品の通報 | **必須** |
| ユーザーのブロック | **必須** |

通報・ブロックをログイン必須にすることで、匿名IDによるなりすまし連投を
防ぎ、かつ運営側が「誰が通報したか」を識別できるようにする。

## 3. YouTube連携・投稿フロー

投稿の都度ではなく、事前にYouTubeアカウント／チャンネルをNIARIMと連携して
おく方式にする。

```text
初回：NIARIM →「YouTubeと連携」→ Googleアカウント認証 → 投稿先チャンネル確認 → 連携完了
以後：作品完成 → NIARIMで「YouTubeに投稿」→ 連携済みチャンネルへ投稿
      → YouTube動画ID取得 → NIARIMに作品登録
```

`youtube.upload`スコープ（YouTube動画の管理権限）を使用する。公開前に
Googleのアプリ確認審査が必要になるため、実装より前に着手すべき別タスクと
して扱う（15章）。

Google OAuthはYouTubeチャンネルへの投稿権限を取得するために使うものであり、
NIARIM独自のユーザーアカウント基盤とは別物として設計する（4章）。将来
YouTube以外の投稿先やNIARIM独自アカウントへ拡張する余地を残すため。

## 4. NIARIM User IDの発行・紐付け

Googleアカウントのメールアドレス等をそのままNIARIMの公開プロフィールとして
使わない。GoogleのIDトークンに含まれる`sub`（アカウント固有の安定した識別子）
をキーとして、NIARIM User ID（ランダムなUUID等）を発行・参照する。

```text
初回投稿時：Google sub → 未登録 → NIARIM User ID発行（例：N000001）
再訪問時　：Google sub → 既存ユーザー → 発行済みのN000001を再利用
```

これにより、再インストール・機種変更・複数端末の利用があっても同一の
NIARIM User IDに紐付けられ、投稿履歴や作者別作品一覧が分断されない。

### Googleアカウントの複数作成による制限回避について

`sub`をキーにした識別は「1つのGoogleアカウントにつき1つのNIARIM User ID」
を保証するが、荒らしが複数のGoogleアカウントを作成すれば、1アカウントあ
たりの投稿制限（11章）自体は回避できてしまう。この方式だけで匿名による
大量投稿を完全に防げるわけではない点は認識しておく。

ただし、以下の組み合わせによって「匿名で何百本も投稿する」タイプの荒らし
は現実的にかなりやりにくくなる。

- 投稿にGoogleアカウント認証が必須（トークン取得の手間がかかる）
- NIARIM User IDごとの投稿上限（11章）に加え、NIARIM全体の1日あたり
  投稿上限（10章）もある二重の制限
- 通報・ブロックがログイン必須で、通報者・被通報者の双方を識別できる
- 運営側でスパム投稿を削除できる（13章）

最初から端末ID・電話番号認証・本人確認などの重い対策を要求すると、NIARIM
の「気軽に描いて遊べる」というUXを壊しやすいため、現段階ではここまでの
対策にとどめる。実際に荒らしが発生した場合の追加対策候補は20章に記載する。

## 5. NIARIM側で保存するデータ（動画ファイル自体は保存しない）

1作品あたりのメタデータは2KB以内に収める方針とする（動画本体・画像本体・
音声本体はDynamoDBに保存しない）。

| 項目 | 用途 |
|------|------|
| NIARIM作品ID（workId） / NIARIM User ID | 作品・投稿者の識別 |
| YouTubeチャンネルID / YouTube動画ID（youtubeVideoId） | YouTube側との紐付け、投稿判定（6章）、冪等登録キー（17章） |
| チャンネル名（channelName） / チャンネルアイコンURL（channelAvatarUrl） / キャッシュ取得日時 | 公開プロフィール表示用（23章）。連携・投稿時に`channels.list`で取得しキャッシュ、閲覧のたびには再取得しない |
| 動画タイトル・投稿日時・YouTube URL・サムネイル情報 | 一覧・詳細表示 |
| 再生回数・高評価数・コメント数・rankingScore | ランキング・詳細表示（8章） |
| ブックマーク数（bookmarkCount） | NIARIM独自のブックマーク機能・ブックマーク数ランキング（8.5節） |
| 最終取得日時 | 統計の鮮度管理 |
| 公開状態（NIARIM側の公開／非公開設定。YouTube側が非公開・削除の場合は表示のみ強制停止） | 掲載可否の判定（13章） |
| 動画の向き（isShort：ショート/横動画の判定結果） | ショートモード表示の絞り込み（8.9節） |
| 通報情報（対象作品ID・通報者のNIARIM User ID・理由・日時・対応状況） | UGC対応（9章） |
| ブロック関係（ブロック元／先のNIARIM User ID） | UGC対応（9章） |
| 日次投稿カウンター（NIARIM User ID単位・NIARIM全体単位、日付キー） | 投稿上限の管理（11章） |
| ブックマーク記録（NIARIM User ID・workId・ブックマーク日時） | どのユーザーがどの作品をブックマーク済みか、二重カウント防止、「ブックマークした作品」一覧表示（8.5節） |

2KB×50万作品で概算約1GB（GSI分のオーバーヘッドを別途見込む必要はあるが、
DynamoDB無料枠の25GBに対して十分余裕がある規模）。

## 6. NIARIM投稿作品であることの判定（持ち込み禁止）

概要欄の文字列やハッシュタグ（例：`#NIARIM`）はユーザーが自由に付けられて
しまうため判定に使えない。**NIARIMのバックエンドが投稿処理の成功時に受け
取ったYouTube動画IDのみをDBへ登録する**方式とし、既存のYouTube動画（既に
大量再生されている動画等）を後から持ち込んでランキングに登録することを
技術的に不可能にする。

### `POST /works`でのvideoId検証（クライアント自己申告を信用しない）

動画本体のアップロード（`videos.insert`）はLambda Function URLの同期呼び出し
ペイロード上限（6MB）を大きく超えるため、Lambdaを経由せず**アプリから
YouTubeへ直接**（ユーザー自身のOAuthトークンでresumable upload）行う。この
ため`POST /works`は「アップロード完了後にvideoIdを添えて登録を依頼する」
という小さなJSONリクエストになるが、**Lambda側はこのvideoIdをクライアント
の自己申告のまま無条件に信用してはいけない**（改造されたクライアントが、
自分の別の古い動画や第三者の人気動画のIDを渡して不正登録することを防ぐ
ため）。

`POST /works`のLambdaハンドラでは、登録前に必ずサーバー側から`videos.list`
（`part=snippet`、クォータ消費は軽微）を呼び、次の2点を検証してから登録する。

- `snippet.channelId`が、そのNIARIM User IDに紐付いている連携済みYouTube
  チャンネルID（3章）と一致すること
- `snippet.publishedAt`が直近（数分〜数十分以内）であること（過去の動画の
  使い回しを防ぐ）

いずれかを満たさない場合は登録を拒否する。この検証と同じタイミングで、
11章の投稿枠予約も行う。

## 7. 統計値の扱い

再生回数・高評価数・コメント数はYouTube側の値をそのまま表示し、NIARIM側で
独自に加算・合算しない。高評価・コメント機能もNIARIM内には実装せず、
YouTube側の機能に一本化する。

一方でブックマークは、YouTube側の高評価とは別のNIARIM独自機能として実装する
（8.5節）。ブックマーク数はYouTube API側に存在しない値のため、NIARIM側で
カウントを保持・管理する。

## 8. ランキング・新着・作者別一覧

累計／年間／月間／週間／デイリーの5種類。表示はいずれもTop 50のみ。

### 8.1 統計更新バッチ（全作品対象）

過去の作品が後から急に伸びるケースを正しく拾うため、統計更新は登録作品を
**全件対象**とする。

```text
DynamoDBを1ページずつScan
  → 各作品のYouTube動画IDをvideos.batchGetStatsへ渡して統計取得
  → rankingScoreを計算
  → 各作品のrankingScore等を更新
```

50万件規模のScanは1回のLambda実行（最大15分）には収まらないため、以下の
方式でページ単位に分割する（Step Functionsは使わず、現行のLambda +
DynamoDB + EventBridge構成のまま完結させる）。

- EventBridge Schedulerは更新サイクルの開始のみをトリガーする。
- Lambdaは1ページ分（DynamoDB Scanの1回のレスポンス分）を処理したら、
  `LastEvaluatedKey`をペイロードに載せて**自分自身を非同期呼び出し
  （`InvocationType=Event`）**し、そのまま終了する。次の呼び出しが続きの
  ページから処理を再開する。
- 無限ループ事故を防ぐため、想定作品数から逆算した最大反復回数のガードを
  入れる。
- Lambdaの非同期呼び出しは失敗時にAWSが自動リトライすることがあるため、
  同一ページが二重に処理される可能性がある。`rankingScore`の更新は
  「最新値で上書き」なので二重処理されても結果は壊れない（冪等）。
- 全ページの処理が完了したら、DynamoDBに「最終更新完了日時」を1件記録する。
  表示側（8.2のGSI Query）が更新途中の中途半端な状態を参照しないよう、
  更新完了後にまとめて反映される設計にする。
- 統計更新時にはvideos.batchGetStatsと併せて動画の公開状態も確認し、
  13章の同期処理を行う。

統計更新に使う読み取り量はDynamoDBの無料枠（25 RCU）を使い切らないよう、
15〜20 RCU程度に抑え、残りを通常利用（閲覧・投稿等）に残す。

### 8.2 ランキング表示（Top 50のみ、GSIを使用）

8.1とは別の処理として扱う。**Top 50を出すためだけに全件Scanは行わない。**
8.1で各作品のrankingScoreを更新する際に、DynamoDBのGSI（rankingScoreを
ソートキーに持つ）へも書き込んでおき、表示時はこのGSIへのQuery1回
（降順・上限50件）で完結させる。

```text
[統計更新] 全作品 → YouTube統計取得 → rankingScore更新（GSIにも反映）
[表示]     GSI Query（rankingScore降順・Top 50） → アプリ
```

**13章の強制非表示対象（YouTube側が非公開・削除）およびNIARIM側で
非公開設定になっている作品は、GSIのソートキー属性（rankingScore）
自体を書き込まない（既存分は削除する）ことでGSIから除外する。**
DynamoDBのGSIは、対象アイテムにソートキー属性が存在しない場合は
そのGSIに射影されない性質を利用しており、表示側のQuery結果には
そもそも含まれないため、Top 50取得後に個別の可視性チェックを挟む
必要がない（Query1回で完結する設計を崩さない）。対象作品が再び
表示可能になった場合は、次回8.1のバッチで通常どおりrankingScore
（＝GSIソートキー属性）を書き戻せば自動的にGSIへ再登録される。

現状の想定成長ペース（11章：無料1日1作品・プレミアム1日3作品、NIARIM全体
1日最大100作品）では、GSIの書き込み集中（ホットパーティション）が問題に
なる水準には当面到達しない見込み。将来作品数・投稿頻度が大きく増えた場合
は、GSIのパーティションキーを分割（シャーディング）する設計への移行を
検討する（20章）。

### 8.3 新着表示

ランキングとは別に、NIARIM DB内の投稿日時のみで表示できる（表示のために
YouTube APIを呼ぶ必要はない）。非公開・削除扱いになった作品は5章の公開
状態フィールドで除外する（13章）。

### 8.4 同一作者の作品一覧

NIARIM User ID・YouTubeチャンネルID・YouTube動画IDの関連付けから導出する。
1作者あたりの件数は11章の投稿上限（無料1日1本・プレミアム1日3本）に
より現実的な範囲に収まるため、8.2のような大規模GSI最適化は不要で、
作者IDをキーにしたQuery結果に対しレスポンス直前で5章の公開状態
フィールドによるフィルタ（非公開・強制非表示の作品を除外）をかける
だけでよい。

### 8.5 ブックマーク機能・ブックマーク数ランキング

YouTube側の高評価（7章）とは別に、NIARIMアプリ内でログイン済みユーザーが
作品を個別にブックマークできる独自機能を実装する。ブックマークには
ログインが必要（2章の閲覧＝ログイン不要、投稿・ブックマーク＝ログイン
必須という区分に合わせる）。

- ブックマーク／解除の操作ごとに、DynamoDBの`TransactWriteItems`で
  「ユーザー別ブックマーク記録（5章）の作成／削除」と「作品側
  `bookmarkCount`の±1」をアトミックに行う。同一ユーザーが同じ作品を
  二重にブックマークしてカウントがずれることを、記録の存在チェックと
  トランザクションの条件付き書き込みで防ぐ。
- `bookmarkCount`はYouTube API由来の値ではなくNIARIM側で直接加算・減算
  するため、8.1の統計更新バッチ（YouTube統計取得）の対象外とし、
  操作直後にほぼリアルタイムで反映される。
- 再生回数ベースのランキング（8.2）と同様に、`bookmarkCount`を
  ソートキーに持つ別のGSIを用意し、表示時はこのGSIへのQuery1回
  （降順・上限50件）で「ブックマーク数ランキング」のTop 50を取得する。
- 初期仕様ではブックマーク数ランキングは累計のみとし、再生回数
  ランキングのような期間別（年間／月間／週間／デイリー）集計への対応は
  20章の検討事項とする。
- ユーザーが自分でブックマークした作品の一覧は、5章のブックマーク記録
  （NIARIM User ID単位）から取得する。
- **ブックマーク一覧の公開設定（Task#164）**：21.2節の調査結果どおり、
  ブックマーク一覧自体に「公開する／しない」の利用者設定を用意し、
  既定値は非公開とする。UI実装済み（現状はダミーデータへのクライアント
  側の一時的な状態。バックエンド実装時は、この設定をユーザープロフィール
  相当のレコードへ持たせ、`GET /users/{id}/bookmarks`相当の一覧取得
  エンドポイントで非公開の場合は403等で拒否する想定）。

### 8.5bis リポスト機能（Task#164）

X（旧Twitter）の「リポスト」と同じ考え方で、ブックマークとは別に
「他者の作品を、自分をフォローしているユーザーへ広める」機能を実装した
（UI実装済み、現状はダミーデータ）。

- リポスト記録（NIARIM User ID・workId・リポスト日時）はブックマーク
  記録（5章）と同じ構造のテーブルで管理する想定。バックエンド実装時は
  `TransactWriteItems`で「リポスト記録の作成／削除」と「作品側
  `repostCount`の±1」をアトミックに行う（8.5のブックマーク実装と同じ
  パターン）
- フォロー中の作者タブ（8.9節相当、Task#144）は、フォロー中の作者
  本人の投稿に加え、フォロー中の作者が他者の作品をリポストした場合も
  一覧に混ぜ、新着順の基準を「投稿日時」と「リポスト日時」のうちより
  新しい方にする。バックエンド実装時は、フォロー中の作者ID一覧に対して
  「本人の投稿一覧」と「本人のリポスト一覧」の両方をクエリし、
  アプリ側（またはLambda側）でマージ・再ソートする想定
- **自分自身が投稿した作品もリポストできる**（Task#134継続で仕様変更。
  「フォロワーへ改めて周知したい」という需要を優先し、投稿者本人にも
  制限しない。フォロー機能とは異なり、リポストは「特定の相手への
  メッセージ」ではなく不特定多数への一方向的な再掲にすぎないため、22章の
  届出義務の境界にも影響しない）

### 8.6 検索（作品タイトル・投稿者名）

新着・ランキングいずれの一覧に対しても、作品タイトルまたは投稿者名の
いずれかに検索語を含む作品へ絞り込める（大小文字を区別しない部分一致、
OR条件）。現状の`community_screen.dart`はバックエンド未実装のためこの
画面が保持するダミーデータへのクライアント側フィルタとして実装されて
おり、期間フィルター（8.1）・ソート順（8.2）と組み合わせて適用される。

バックエンド実装後は、全件Scanを避けるため次のいずれかの方式を想定する。

- 小規模〜中規模（数万件程度まで）：`GET /works/latest`・
  `GET /ranking/{period}`へ検索クエリパラメータ（`q`）を追加し、
  Lambda側でDynamoDB取得後にアプリ側と同様の部分一致フィルタをかける
  （8.2のGSI Query結果Top 50に対してフィルタするため、検索語に一致する
  作品がTop 50圏外にあると見つからない制約が残る。初期規模では許容）
- 大規模化した場合：OpenSearch Service等の全文検索基盤への索引作成を
  別途検討する（20章の将来課題に追加）

### 8.7 タグ機能（クラウド編集タグ）

ニコニコ動画・pixivのタグロック機能と同様、作品に対して**誰でもタグを
追加・削除でき、投稿者のみ特定のタグをロックしてほかのユーザーの削除を
防げる**機能。タグをタップする、または検索ボックスをタグ検索モードへ
切り替えることで、そのタグを持つ作品のみへ絞り込める（8.6の検索とは
別の絞り込み軸として並存する）。

（法的検討）この「誰でも編集可・投稿者はロック可」という設計自体は
ニコニコ動画・pixivが長年公開運用している一般的なUXパターンであり、
実際にWeb検索で確認した結果、特許・商標上の懸念は低いと判断した
（詳細な調査結果はセッションのやり取りに記録。folksonomy自体も
del.icio.us以来の公知技術）。

現状の`community_screen.dart`はバックエンド未実装のため、この画面が
保持するダミーデータへのクライアント側の一時的な状態変更として実装
されている（`CommunityWork.tags`/`lockedTags`、ブックマークと同様に
アプリ再起動やこの画面を離れると元に戻る）。投稿者本人かどうかの判定は、
実際のログイン基盤（4章のNIARIM User ID）が無いため、UI確認用の仮の
自分自身のID（`kDummySelfAuthorId`）と`work.authorId`の比較で代用して
いる。実装後は認証済みのNIARIM User IDへ置き換える。

バックエンド実装時の設計方針（$0運用方針を維持する前提）：

- タグの追加・削除・ロック切り替えは`PATCH /works/{id}/tags`のような
  専用エンドポイントを想定し、5章の作品データへ`tags`（文字列配列）・
  `lockedTags`（文字列配列）フィールドを追加する
- リアルタイム同期は必須としない。ユーザーがタグを編集した時点の状態を
  即時反映するか、他の閲覧中ユーザーの画面には次回一覧取得時
  （バッチ的な再取得）に反映される形で許容する（DynamoDBの
  `ConditionExpression`による楽観的な二重更新対策は必要）
- 投稿者本人によるロック操作は、書き込み系エンドポイント共通の
  NIARIM User ID検証（16章）で`work.authorId`と一致するかを確認する
- タグでの絞り込み検索も8.6と同様、初期規模ではLambda側でのアプリ内
  フィルタで対応し、大規模化時に全文検索基盤へ移行する

### 8.8 フローティング動画プレビュー・作品詳細画面

新着・ランキングの作品カードをタップしても、いきなり詳細画面へ遷移
させない。代わりに画面の隅にフローティングウィンドウ
（`CommunityFloatingPreview`）を表示し、動画を再生したまま他の画面
（ホーム等）を閲覧し続けられるようにする。ウィンドウはドラッグで移動、
右下コーナーのハンドルでリサイズでき、閉じる（×）ボタンと「詳細へ」
ボタンを持つ。「詳細へ」から作品詳細画面（`CommunityWorkDetailScreen`、
別ルート`/community/work/:id`）へ遷移する。

- **状態管理**：フローティングウィンドウの表示状態（どの作品か・
  位置・サイズ）は`CommunityPreviewService`（アプリ全体のProvider）が
  保持する。特定の画面のStateではなくアプリ全体で共有することで、
  画面遷移をまたいでウィンドウが表示され続ける要件を満たしている。
  `app.dart`の`MaterialApp.router`の`builder`（ルーティングされる画面の
  外側の層）にStackで重ねて描画する
- **作品データの共有元**：タグ編集・ブックマークを含む作品データ
  （`CommunityService`）も同様にアプリ全体のProviderへ引き上げた
  （以前は`CommunityScreen`のState内にローカルで保持していたが、
  フローティングウィンドウ・作品詳細画面・ホームの「ブクマ済み」タブの
  いずれからも同じ状態を参照・編集できる必要があるため）
- **タグタップでの遷移**：作品詳細画面でタグをタップすると、
  `appRouter.go('/community', extra: tag)`でコミュニティ画面へ戻り、
  そのタグでのタグ検索モードを初期状態として渡す
  （`CommunityScreen.initialTagFilter`）。詳細画面はプッシュされた別
  ルートであり、常にコミュニティ画面のインスタンスが生きているとは
  限らない（フローティングウィンドウ経由で他の画面から詳細画面へ直接
  遷移することもあるため）ため、メソッド直接呼び出しではなくルート引数
  経由でこの初期値を渡している
- **作品詳細画面の内容**：リサイズ可能なプレビュー（タイムラインモード
  のプレビュードラッグハンドルと同じ操作感）・タイトル・投稿日・
  投稿者（タップで投稿者別作品一覧へ、アイコンは現状ダミーデータに
  画像が無いため頭文字アバターにフォールバック）・YouTubeいいね数
  （API生値をそのまま表示）・タグ（タップで絞り込み、誰でも追加削除可、
  投稿者はロック可）・ブックマークボタンとNIARIM独自のブックマーク数・
  通報／ブロックボタンを表示する
- **ホームの「ブクマ済み」タブとの連携**：`home_screen.dart`の
  `_BookmarkedTab`は、以前は「準備中」の案内のみを表示する器だったが、
  `CommunityService`が共有Providerになったことで実際にブックマーク
  済み作品の一覧（`CommunityWorkGrid`）を表示するよう接続した。1件も
  ブックマークしていない場合は従来どおりの案内表示を維持する
- **実際の動画本体は無い**：バックエンド未実装のため、フローティング
  ウィンドウ・詳細画面いずれのプレビューも既存の一覧と同じプレース
  ホルダー（グラデーション＋再生アイコン）を表示する。実際にYouTube
  動画を埋め込む際は、YouTube自身のミニプレイヤー機能に類似する特許
  （Google保有、法的検討はセッションのやり取りに記録）を踏まえ、この
  ウィジェットのような独自ドラッグ実装をそのまま流用するのではなく、
  OS標準のPicture-in-Picture APIへ乗せる方針を検討すること

### 8.9 ショートモード（縦スクロール連続再生）

新着・ランキング・投稿者別作品一覧の各画面から、ボタン1つで
YouTubeショート／TikTok／Instagramリール風の全画面縦スクロール
連続再生ビューアへ切り替えられる。

- **横動画/ショートの判定方法**：YouTube Data APIには「これはShorts
  動画である」という直接のフラグが存在しない（YouTube自身も動画の
  長さ・アスペクト比から内部的に判定している）。一方NIARIM側は、
  投稿元となるプロジェクトのキャンバスサイズ（`drawingWidth`/
  `drawingHeight`）を投稿時点で把握しているため、縦長（高さ＞幅）か
  どうかで確実に判定できる。この判定結果（`isShort`）を作品データ
  （5章の表）へ保持し、YouTube APIへの追加問い合わせなしに一覧側で
  絞り込む
- **絞り込み**：ショートモードを開いた時点の一覧（検索・期間フィルター
  適用後）から`isShort`の作品のみを抽出して渡す。該当作品が1件も無い
  場合はその旨を案内する
- **ビューア**：縦方向`PageView`で次々に作品を切り替える。右側に
  ブックマーク・再生数の縦アクションバー、下部に作者名・タイトル・
  詳細画面への導線を表示する。実際の動画本体（YouTube埋め込み）は
  バックエンド未実装のため、既存の一覧・フローティングプレビューと
  同じプレースホルダー表示を全画面で使う

## 9. UGC（ユーザー生成コンテンツ）対応

NIARIM内の新着・ランキング・作者別作品一覧で他ユーザーの投稿作品を見せる
以上、ストアのUGCポリシー対象として設計する（動画本体をNIARIMがホスト
していないことは免除理由にならない。Google Playだけでなく、将来iOS版を
出す場合はAppleのガイドライン1.2も対象になる）。最低限、以下をアプリ内
機能として用意する。

- **作品を報告**（ログイン必須）：作品詳細画面から通報を送信し、NIARIM側
  DBに通報者のNIARIM User ID付きで保存する（5章）。運営が確認し、問題が
  あればNIARIM内の一覧から除外する（YouTube側の動画自体は削除しない。
  除外はNIARIM内の掲載可否のみを指す）。
- **ユーザーをブロック**（ログイン必須）：ブロックした相手の作品をNIARIM内
  の一覧・ランキングから自分に対して非表示にする。
- **運営対応の記録**：通報の対応状況（未対応／確認中／対応済み）をDB上で
  追跡できるようにする。
- 通報者を識別できるため、実装時には同一ユーザーからの連続通報に対する
  簡易なレート制限も入れておく（20章）。

YouTube動画自体に問題がある場合は、YouTube側の報告機能の利用も別途案内する。

## 10. YouTube Data API のクォータ

統計取得には`videos.batchGetStats`を使う。

| メソッド | クォータ | 備考 |
|---------|---------|------|
| `videos.batchGetStats` | 専用バケットで10,000ユニット/日（1回1ユニット） | 2026年6月3日追加。他メソッドとは別枠。統計の一括取得用途 |
| `videos.insert`（動画投稿） | 専用バケットで100ユニット/日（1回1ユニット＝1日100件まで） | 2025年12月ごろに約1,600ユニット→約100ユニットへ引き下げ済み。**統計取得用クォータとは完全に別枠** |
| `videos.list`（公開状態確認・投稿時のvideoId検証） | 通常クォータ、1回1ユニット程度と軽量 | 6章・13章で使用 |

上記はGoogle公式ドキュメントで裏取り済み（2026年8月時点）。

### 統計更新の呼び出し数試算（100件ずつ取得する場合）

| 作品数 | 1回の更新あたりcall数 | 1日1回 | 1日2回 | 1日3回 | 1日4回 |
|-------|--------------------:|------:|------:|------:|------:|
| 10,000作品 | 100 | 100 units | 200 units | 300 units | 400 units |
| 500,000作品 | 5,000 | 5,000 units | **10,000 units** | 15,000 units | 20,000 units |

50万作品規模では、1日2回の更新でデフォルトの10,000ユニット/日にちょうど
到達する。なお11章の投稿上限から逆算すると、50万作品への到達には長い年月
を要するため、統計更新頻度の上限問題（1日2回ライン）に実際に到達するのは
かなり先になる見込み。

## 11. YouTube投稿の上限

`videos.insert`が専用クォータで1日100件までという制約（10章）を踏まえ、
NIARIM側でも会員種別ごとの投稿上限を設ける。

### 11.1 初期仕様

| 項目 | 無料会員 | プレミアム会員 |
|------|--------:|-----------:|
| YouTubeへのNIARIM投稿 | **1日1作品** | **1日3作品** |
| NIARIM全体の投稿上限 | 1日最大100作品（会員種別に関わらず共有） | 同左 |

NIARIMは「短時間で大量の動画を投稿するSNS」ではなく「アニメーションを
制作して完成した作品を公開するアプリ」であるため、無料会員の1日1作品は
通常の利用者にはほとんど制約に感じられない一方、荒らし・スパム投稿には
十分に効く。

この制限は**最初から適用する**（後から「制限なしで盛り上げてから絞る」
ことはしない）。後から制限を追加すると既存ユーザーの不満につながるため、
「無料会員は1日1作品まで」という説明のほうが定着しやすい。プレミアム
会員が1日3作品というのは、プレミアム会員特典の一つにもなる。

### 11.2 段階的な引き上げ・引き下げ方針

NIARIM全体の1日100作品という枠が恒常的に逼迫した場合、次の順で対応する。

| 段階 | 無料会員 | プレミアム会員 | 実施タイミング |
|------|--------:|-----------:|--------------|
| 初期仕様（11.1） | 1日1作品 | 1日3作品 | サービス開始時から |
| 第2段階 | 週1作品 | 1日1作品 | NIARIM全体の投稿数が恒常的に100件/日に近づいた場合 |
| 第3段階以降 | 上限緩和を検討 | 上限緩和を検討 | 実際の利用状況を見て個別に判断 |
| クォータ増枠検討 | — | — | 十分な規模・収益が確立し、Googleへの増枠申請の審査要件（YouTube OAuth審査、12・15章）に対応できる段階 |

第2段階（無料：週1作品、プレミアム：1日1作品）まで制限しても100件/日を
継続的に使い切るようなら、それはNIARIMに十分な投稿需要があるということ
であり、その段階でYouTube APIのクォータ増枠を検討する。

YouTube Data APIのクォータ増枠はGoogle側の審査が関係するため、**「お金を
払えば100件→1000件に増える」といった単純な従量課金ではない**点に注意する
（10章）。将来的には次の順で安全に対応する。

```text
① 投稿制限を調整（11.2の段階的引き下げ）
② YouTubeクォータ増枠を検討
③ 必要ならGoogle側の審査・要件に対応
④ サービス規模に応じて運営費（増枠後の運用コスト等）を許容
```

### 11.3 100件/日消費イメージ（初期仕様の場合）

無料70人が1作品ずつ、プレミアム10人が3作品ずつ投稿すると
`70 + 30 = 100作品`でその日の受付は終了する。ただし実際には全員が毎日
投稿するわけではないため、登録ユーザー数が100人を超えた時点で即座に枠が
埋まるわけではない。重要なのは実際の1日あたり投稿数であり、内部的には

```text
当日投稿数 0～69   → 通常
当日投稿数 70～89  → 注意（監視強化）
当日投稿数 90～99  → 残り枠僅少
当日投稿数 100     → 本日受付終了
```

のように段階を管理できるが、ユーザーへ「残り○枠」をリアルタイム表示する
必要はない。上限に達した場合は単に「本日の公開上限に達しました。明日また
投稿できます。」と案内すれば十分。

## 12. 投稿枠の消費ルールと原子的な予約

### 12.1 非公開・削除しても投稿枠は戻らない

**YouTubeへの新規投稿（`videos.insert`）が成功した時点で、その日の投稿枠
（NIARIM User ID単位・NIARIM全体単位の両方）を1つ消費する。** その後に
作品を非公開にしても削除しても、消費済みの投稿枠は復活しない。

これを保証しない場合、「投稿→非公開→再投稿」を繰り返すだけで11章の1日
あたり投稿上限を簡単に突破できてしまう。

### 12.2 投稿枠の原子的な予約

`POST /works`（6章）のLambdaハンドラでは、実際のYouTubeアップロードより
前に投稿枠を予約する。

```text
① Google認証
② NIARIM User ID確認
③ 当該NIARIM User IDの本日の投稿数を確認（11.1の上限と比較）
④ NIARIM全体の本日の投稿数を確認（1日100作品の上限と比較）
⑤ いずれも上限未満なら、両方のカウンターをアトミックにインクリメントして枠を確保
⑥ YouTubeへアップロード（アプリから直接）
⑦ アップロード成功 → videoId検証（6章）→ NIARIM DBへ登録
```

DynamoDBの条件付き書き込み（`ConditionExpression`）を使い、日次カウンター
の更新を「上限未満の場合のみインクリメントする」形でアトミックに行うこと
で、100件目と101件目の投稿が同時に行われた場合でも100件を超えないよう
にする。

アップロード自体が失敗した場合（⑥で失敗）は、予約した枠を解放する（⑤で
確保したカウンターを1つ戻す）ことも合わせて実装する。

## 13. 作品の公開・非公開・削除

「非公開」と「削除」を明確に分ける。

| 操作 | YouTube動画本体 | NIARIM内の新着・ランキング・作者一覧 |
|------|---------------|--------------------------------|
| 非公開 | 残す | 除外（後で再公開可能） |
| 削除 | ユーザーが希望すればYouTube側も削除（`videos.delete`） | 除外（紐付けも解除） |

| 機能 | 無料会員 | プレミアム会員 |
|------|:-------:|:-----------:|
| NIARIM内で公開 | ○ | ○ |
| NIARIM内で非公開 | ○ | ○ |
| NIARIM内からYouTube動画を削除 | ○ | ○ |
| 再公開 | ○（投稿枠は消費しない。12.1のとおり新規投稿時のみ枠を消費するため） | ○ |
| 投稿済み作品のメタデータ編集（タイトル等） | ○ | ○ |

再公開・非公開・メタデータ編集は`videos.insert`を使わないため、11章の
投稿上限には影響しない。

### YouTube側で状態が変更された場合の追随

ユーザーがYouTube Studio側から動画の状態を変更した場合、8.1の統計更新
バッチ（`videos.batchGetStats`と併せて`videos.list`等で状態も確認）で
検知し、NIARIM側の表示へ反映する。

「NIARIM内で公開／非公開にできる」（本章冒頭の機能表）は、
YouTube側の状態に関わらずユーザーが自由に切り替えられる**独立した設定**
とする。YouTube側の状態は、その独立設定を「上書きしてでも強制的に
非表示にすべきか」の判定にのみ使う。

- **限定公開はYouTube視聴用URLが生き続けるため、NIARIM側の公開設定を
  上書きしない。** NIARIM内で「公開」を選んでいれば、YouTube上は限定
  公開のままでもNIARIM内では通常どおり再生・表示できる。これにより、
  「YouTubeの検索・おすすめには出したくないが、NIARIMというアプリ内
  だけでは見てもらいたい」という需要に応えられる（YouTube側を限定公開に
  しておけば、NIARIM経由以外の第三者がYouTube上でこの動画を発見する
  経路はほぼ塞がる）。
- **非公開（Private）・削除済みは再生用URL自体が機能しなくなる**ため、
  NIARIM内の設定に関わらず強制的に非表示（無効化）する。ユーザーの
  NIARIM側公開設定は保持したまま（データは消さない）表示のみ止め、
  YouTube側が公開または限定公開へ戻れば自動的に表示が復帰する
  （非公開・限定公開間の行き来は`videos.list`の`status.privacyStatus`
  で判定できる）。

| YouTube側の状態 | 再生用URLの生死 | NIARIM側の扱い |
|----------------|----------------|---------------|
| 公開 | 生きている | NIARIM側の公開設定（公開／非公開）どおりに表示 |
| 限定公開 | 生きている（URLを知っていれば誰でも視聴可） | NIARIM側の公開設定どおりに表示（YouTube側は非公開のままでよい） |
| 非公開 | 機能しない（所有者以外は再生不可） | 強制的に非表示（NIARIM側の設定は保持し、状態が戻れば復帰） |
| YouTubeから削除済み | 存在しない | NIARIMの投稿情報も無効化・非表示（紐付け解除） |

想定される利用パターン：

| 用途 | YouTube側設定 | NIARIM側設定 |
|------|-------------|-------------|
| 一般公開（YouTube上でも誰でも見つけられてよい） | 公開 | 公開 |
| 知り合いだけに見せたい（YouTubeのURLを直接共有し、NIARIMのコミュニティ一覧には出さない） | 限定公開 | 非公開 |
| YouTube単体では一般公開したくないが、NIARIMのコミュニティ機能内でなら公開したい | 限定公開 | 公開 |
| 一時的に取り下げたい（作り直し中等） | 公開のまま可 | 非公開 |

限定公開を「NIARIM側でも自動的に非公開扱いにする」旧方針は撤回した
（旧方針では上記表の3行目のニーズに応えられなかったため。旧方針の
「YouTube側の状態変更だけでNIARIM側のデータが失われる事態を避ける」
という目的自体は、削除以外はデータを消さず表示のみ止める現行方針でも
引き続き満たされる）。

### フォロワー限定公開（見送り）

「特定のフォロワーにだけ公開したい」という需要も想定はできるが、初期
仕様には含めない。理由：

- **YouTube API Developer Policies違反の懸念（最重要）**：YouTube Data
  APIの開発者向けポリシーには「再生ボタンを押す以外の操作をユーザーに
  要求してYouTube動画の視聴・再生継続をゲート（制限）してはならない」
  という趣旨の制約がある（出典：
  [YouTube API Services - Developer Policies](https://developers.google.com/youtube/terms/developer-policies)、
  [Complying with YouTube's Developer Policies](https://developers.google.com/youtube/terms/developer-policies-guide)）。
  「フォロー済みでなければNIARIM内で再生できない」という制限は、この
  「再生ボタン以外の操作を要求してはならない」に該当する可能性が高く、
  仮に技術的に実現できても**YouTube API利用規約違反として審査（15章）
  で問題になる、またはAPIアクセスを停止されるリスク**がある。この点は
  下記の閲覧ログイン不要の設計原則とは独立した、YouTube側の規約に
  起因するより強い禁止事由であり、追加検討する場合はこの制約の解消
  （例：NIARIM内での視聴制限ではなく単なる一覧上の非表示にとどめる等）
  が前提になる。
- 2章の設計原則「閲覧にはログイン不要」を維持する場合、フォロワー限定
  作品を表示するにはその一覧取得リクエストの時点で**閲覧者自身の
  ログイン・NIARIM User ID**が必要になり、既存の「読み取り系エンド
  ポイントは匿名利用を許可する」（16章）という設計を作品ごとに部分的に
  崩すことになる（フォロワー限定作品が1件でも一覧に混ざる可能性がある
  以上、一覧取得エンドポイント自体に認証つき呼び出しの経路を用意する
  必要が生じる）。
- 前提となる「フォロー（お気に入り作者）」関係の保存・判定自体が
  #144（お気に入り作者機能）で未着手。
- DynamoDB上でも「その閲覧者がその作者をフォロー済みか」を作品一覧の
  都度チェックする必要があり、8.2のGSI Query（Top 50を1回のQueryで
  完結させる設計）のようなシンプルな読み取りでは済まなくなる。

$0運用・閲覧ログイン不要という現行方針を崩さない範囲では実現が難しい
ため、需要が明確になった段階で改めて設計を検討する（20章へ追記）。

## 14. ランキング更新頻度

初期は1日2〜4回を選択できる設計にしておき、作品数が増えてきたら1日2回を
基本とする。50万作品規模に到達した場合、1日2回がデフォルトクォータ枠の
上限ライン（10章）。

## 15. YouTube OAuth審査（公開前の必須タスク）

`youtube.upload`スコープは制限付きスコープであり、一般公開アプリで使用する
にはGoogleのアプリ確認審査が必要になる。実装後ではなく、公開前の重要タスク
として次の順で進める。

```text
① Google Cloudプロジェクト作成
② YouTube Data API有効化
③ OAuth同意画面の設定
④ OAuthクライアントの作成
⑤ youtube.uploadスコープの申請理由整理
⑥ テストユーザーでの動作確認
⑦ Googleのアプリ確認審査・公開要件の確認
```

審査には利用規約・プライバシーポリシーの提示、スコープの利用目的を示す
説明動画の提出などが必要で、数週間かかる場合がある。想定ユーザー数次第では
追加のセキュリティ評価（CASA）が必要になる可能性もある。

## 16. バックエンド構成

DynamoDBへアプリから直接アクセスする構成にはしない。API Gatewayは使わず、
**Lambda Function URL**（Lambda関数にHTTPSエンドポイントを直接付与できる
仕組み）をAPI層として採用する（「できる限り無料で運用する」方針を優先）。

```text
NIARIM App
   │ HTTPS
   ▼
Lambda Function URL（AuthType: NONE）
   ▼
1つのLambda内にAPIルーター（method + pathで振り分け）
   ├─ GET    /ranking/daily 等 → ランキング表示（8.2）
   ├─ GET    /works/latest      → 新着表示（8.3）
   ├─ GET    /users/{id}/works  → 作者別作品一覧（8.4）
   ├─ POST   /works             → 作品登録（videoId所有者検証は6章、投稿枠予約は12章、冪等登録は17章）
   ├─ PATCH  /works/{id}        → 公開／非公開切り替え・メタデータ編集（13章）
   ├─ DELETE /works/{id}        → 削除（NIARIM紐付け解除、必要ならYouTube側も削除。13章）
   ├─ POST   /reports           → 通報（要ログイン、9章）
   └─ POST   /blocks            → ブロック（要ログイン、9章）
   ▼
DynamoDB

EventBridge Scheduler（1日2〜4回）
   ▼
ランキング更新Lambda（8.1の自己再帰呼び出しでページ分割処理）
   ├→ YouTube API（videos.batchGetStats・videos.list）
   └→ DynamoDB（統計・rankingScore・GSI・公開状態・更新）
```

Function URLの`AuthType`は`NONE`（AWS認証なしの公開エンドポイント）を使う。
アプリに秘密鍵を埋め込んでAPI認証に使う方式は採用しない（APKやIPAから解析
される可能性があるため）。読み取り系（ランキング・新着等）は匿名利用を
許可し、書き込み系（投稿・通報・ブロック・公開状態変更）はNIARIM User ID
（4章）を用いたリクエスト検証・レート制限をLambda側で実装する。API
Gatewayの使用量プラン・WAF等は、将来より高度なAPI管理が必要になった場合
の追加候補とする。

## 17. データ整合性（YouTube投稿成功→DB登録失敗の対策）

YouTubeへの投稿自体は成功したが、その後のNIARIM DB登録が通信エラー等で
失敗するケースを想定し、`youtubeVideoId`を冪等キーとして扱う。

```text
① YouTube投稿 → ② videoId取得 → ③ NIARIM DB登録
```

③が失敗した場合はvideoIdを使って再試行する。DB側は「videoIdが既に登録
済みなら更新、未登録なら新規登録」として扱うため、再試行しても同一作品が
二重登録されない。

## 18. 利用規約・プライバシーポリシーへの反映が必要な点

現行の規約・プライバシーポリシーには「本アプリは作成コンテンツを開発者の
サーバーへ送信・収集・同期する機能を提供していません」という趣旨の記述が
ある。本機能を実装すると、この記述はそのままでは不正確になる。

反映時は次の2点を明確に分けて記載する。

- 作品データそのもの（動画ファイル・プロジェクトデータ）はNIARIMのサーバー
  には保存しない（引き続き維持される方針）。
- 公開作品に関するメタデータ（YouTube動画ID・チャンネル識別情報・タイトル・
  統計情報・掲載情報・通報情報等）と、投稿・通報・ブロック機能利用時に
  発行されるNIARIM User IDはNIARIMのサーバー（DynamoDB）で管理する
  （本機能で新たに追加される事実）。

UGC対応（9章：通報・ブロック・運営対応）、投稿上限（11章）、削除時に
YouTube動画も削除される場合がある旨（13章）についても、規約側に利用条件
として明記する。

## 21. ブックマーク通知・被ブックマーク一覧・ユーザー別ブックマーク一覧の実現可否（Task#145）

「サーバー代0円で実現できるか」という観点での調査。結論として、3機能
とも追加のサーバー費用0円で実現可能。既存のLambda Function URL（常時
無料枠：月100万リクエスト＋40万GB秒）とDynamoDB（常時無料枠：25GB・
25RCU・25WCU、5章）の枠内に収まる設計にできる。ただし「サーバー代」
以外の観点（プライバシー設計・新規実装コスト）で個別に検討が必要な
点が残るため、以下にまとめる。

### 21.1 被ブックマーク一覧（自分の作品を誰がブックマークしたか）

5章のブックマーク記録（NIARIM User ID・workId・ブックマーク日時）に
対して、workIdをパーティションキーとする逆引き用GSI
（`GSI-BookmarksByWork`：PK=workId、SK=bookmarkedAt）を追加すれば、
「この作品をブックマークしたユーザー一覧」をQuery1回で取得できる。
8.2のランキング表示・8.5のブックマーク数ランキングと同じ「GSIへの
Query」パターンの踏襲であり、設計上の新規性はない。

GSIは書き込み量を消費する（レコード作成のたびにベーステーブルとGSI
双方への書き込みが走る）ため、GSIを1本追加するごとに25WCUの常時無料枠
を分け合う形になる。現状すでにブックマーク数ランキング用GSI（8.5）・
再生回数ランキング用GSI（8.2）等、複数GSIを前提とした設計であり、
被ブックマーク一覧用GSIを1本追加してもブックマーク操作1回あたりの
追加書き込みが1件増えるのみで、書き込みパターン自体は変わらない
ため、25WCUの枠に収まる限りは実質的な追加コストは発生しない。

表示上の注意点：ブックマークしたユーザーの識別情報として現状NIARIM
User IDしか無く、公開プロフィール（表示名・アイコン）の仕組みが
存在しない（4章）。「誰が」を作者に見せる機能にする場合は、最低限
「ブックマークされた総数の推移が分かる」程度に留めるか、公開
プロフィール機能（未着手）を別途設計する必要がある。

### 21.2 ユーザー別ブックマーク一覧（任意のユーザーのブックマーク一覧を閲覧）

8.5の「自分でブックマークした作品の一覧」は、ブックマーク記録テーブル
をNIARIM User ID（パーティションキー）で引くQueryとして設計済み。
これを「呼び出し元自身のIDに固定」ではなく「パスパラメータで指定した
任意のuserId」に対して同じQueryを許可すれば、技術的にはそのまま
「ユーザー別ブックマーク一覧」になる。追加コストは発生しない（既存の
Queryパターンの再利用）。

ただし、これは技術的な可否とは別に**プロダクト判断が必要**：「何を
ブックマークしたか」は他人の趣味嗜好を推測できる情報であり、本人の
許可なく誰でも閲覧できる状態にするのはプライバシー上望ましくない
可能性がある。13章で作品側にすでに「NIARIM独自の公開／非公開」設定が
あるのと同様に、ブックマーク一覧自体にも「公開する／しない」の利用者
設定を用意し、既定値は非公開にすることを推奨する（Task#144で実装した
フォロー機能も、フォロー関係自体は現状どちらの当事者にも一覧を公開
しない設計にしている）。

### 21.3 ブックマーク通知（自分の作品がブックマークされたら通知）

「通知」を実現する方式は大きく2通りあり、コスト面の結論は異なる。

- **方式A：アプリ内通知一覧（ポーリング方式）**：ブックマーク操作の
  `TransactWriteItems`（8.5）に「通知テーブルへの1件追加」を含める。
  通知テーブルはDynamoDBのTTL属性（無料機能。期限切れ項目を自動削除）
  を使い、例えば30日で自動失効させれば、通知が無限に溜まってストレージ
  を圧迫することもない。アプリはホーム画面表示時などに
  `GET /users/{id}/notifications`を1回呼ぶだけでよく、追加の常駐サービス
  は不要。**追加費用0円**（既存のLambda Function URL・DynamoDBの
  常時無料枠内に収まる、新規の外部サービスも不要）。
- **方式B：プッシュ通知（アプリを開いていなくても端末に届く）**：
  Firebase Cloud Messaging（FCM）はメッセージ配信自体は無料（送信数に
  よる課金なし）だが、**このリポジトリには現状Firebaseの導入が一切ない**
  （AdMob等の既存SDKはFirebase非依存で組み込まれている）。実現には
  Firebaseプロジェクトの新規作成、Android/iOS双方への組み込み、
  iOS 13+/Android 13+の通知権限リクエストフロー、端末トークンの
  取得・DynamoDBへの保存・失効時のローテーション処理、Lambda側から
  FCM HTTP v1 APIを呼ぶ送信処理一式が新規に必要になる。**サーバー費用
  自体は0円のまま実現できる**が、「サーバー代」以外の新規実装コストが
  方式Aに比べて大きい。

推奨：初期実装は方式A（アプリ内通知一覧）とし、方式Bはニーズが明確に
なった段階の追加検討事項とする（20章の他の見送り項目と同じ位置づけ）。

### まとめ

| 機能 | サーバー費用0円での実現可否 | 備考 |
|------|----------------------------|------|
| 被ブックマーク一覧 | 可能（追加GSI1本、25WCU枠内） | 公開プロフィール未整備のため表示内容は要検討 |
| ユーザー別ブックマーク一覧 | 可能（既存Queryの再利用） | プライバシー面から既定非公開を推奨 |
| ブックマーク通知（アプリ内） | 可能（TTL付き通知テーブル） | 推奨方式 |
| ブックマーク通知（プッシュ） | サーバー費用は0円だが新規実装コスト大 | Firebase未導入のため将来検討 |

## 22. 電気通信事業法の届出義務を発生させないための設計上の境界線

ユーザーからの「通報・ブロック機能は維持したいが、電気通信事業法の
届出義務は発生させたくない」という要望を受けた整理。専門家（弁護士・
行政書士）による正式な法的確認を経たものではなく、あくまで一般的な
解釈に基づく設計指針として記録する。実際の公開前には専門家への確認を
推奨する。

### 22.1 判断基準（一般的な解釈）

電気通信事業法上の届出（16条）が問題になるのは、「他人の通信を媒介する」
サービス、すなわち**特定の相手（1人または少数の特定者）に向けたメッセージ
の伝達を仲介する機能**（メール・チャット・DM等）を提供する場合が中心と
解されている。これに対し、**不特定多数が閲覧できる形での一方向的な情報の
公開・発信**（ブログ、動画投稿、誰でも見られる掲示板への書き込み等）は、
一般に「他人の通信の媒介」には該当しないと解されている（新聞の読者投稿欄が
電気通信事業に該当しないのと同じ考え方）。

### 22.2 NIARIMの現状設計がこの境界線の内側にある理由

- **作品の投稿・閲覧**：投稿された作品は不特定多数が閲覧できる形で公開される
  （特定の1人に宛てて送るものではない）。
- **通報機能**：通報は他のユーザーにではなく、常に開発者（運営）へ送られる。
  ユーザー間の通信を媒介するものではない。
- **ブロック機能**：ブロックした相手の投稿を自分の一覧から除外するだけの
  端末（またはアカウント）側のローカルなフィルタリングであり、相手への
  メッセージ送信や通信の仲介は発生しない。
- **フォロー機能**：フォロー関係は「自分が見る一覧の並び順を変える」個人設定
  にすぎず、フォロー関係自体はどちらの当事者にも公開しない設計（4章・
  Task#144）。ユーザー間でメッセージを媒介する機能ではない。
- **ブックマーク機能（通知・一覧含む）**：いずれも「自分の操作の記録」または
  「運営からの通知」であり、ユーザー間の直接的な通信ではない。

### 22.3 今後、絶対に避けるべき機能（追加すると届出義務が発生しうる）

以下は、上記の判断基準に照らして「特定の相手への通信を仲介する」機能に
該当する可能性が高く、追加する場合は事前に専門家へ確認すべきもの。

- ダイレクトメッセージ（DM）・個人間チャット機能
- 特定ユーザー間だけで閲覧できる非公開グループチャット
- 「特定の相手にだけ見える返信」機能（不特定多数に公開される返信・
  コメントは該当しないと解されるが、送信先を1人に絞った非公開の返信は
  該当しうる）
- その他、送信者が特定の受信者を指定してメッセージを送る機能全般

現状の設計（投稿・閲覧・通報・ブロック・フォロー・ブックマーク）は
いずれも上記に該当しないため、これらを維持する限りは届出義務は
発生しないと考えられる。ただし将来的にDM機能等の追加を検討する場合は、
着手前に必ず本章を参照し、専門家へ確認すること。

### 22.4 「フォロー中/フォロワー一覧・ブックマーク一覧を公開すると届出義務に近づくのか」の整理

結論：**22.1の判断基準（特定の相手への通信の仲介か否か）に照らす限り、
これらを公開しても電気通信事業法の届出義務には直接結び付かない。**
フォロー関係の公開・ブックマーク一覧の公開は、いずれも「誰が誰を
フォローしているか／誰が何をブックマークしたか」という**既存の関係性を
不特定多数に一方向的に開示する**行為であり、22.1が想定する「メッセージを
特定の相手へ届ける」仲介行為そのものではないため。

ただし、これらを公開しない設計にしている理由は届出義務の回避**だけ**
ではない。以下のような、届出義務とは別の実務的リスクが主な理由である。

- **プロフィール公開設定の8.5節・21.2節（ユーザー別ブックマーク一覧）の
  検討時に整理した通り**、フォロワー一覧・ブックマーク一覧の公開は
  ストーキング・晒し上げ・特定のユーザーへの粘着的な監視といった
  UGC（9章）上のリスクを増やす（「このユーザーは普段どの作品を
  ブックマークしているか」が誰でも分かる状態は、通報・ブロック機能だけ
  では防ぎきれない実害につながりやすい）。
- Google Play UGCポリシー・Apple Guideline 1.2の審査は、届出義務のような
  法律上の形式要件だけでなく、実際の悪用可能性（晒し上げ等）も個別に
  審査対象とするため、公開範囲を広げるほど審査上の説明負担・リスクが
  増える。
- フォロー機能自体、13章末尾で見送った「フォロワー限定公開」の前提
  条件でもあり、関係を公開すると将来その方向へ機能を広げたくなる
  誘因が生まれやすい（フォロワー限定公開自体はYouTube API規約上の
  懸念（13章）があるため、そちらへ広げないよう現状の非公開設計を
  維持する）。

まとめると、**フォロー/フォロワー一覧・ブックマーク一覧を非公開にして
いるのは電気通信事業法の届出義務を避けるためではなく、UGCリスク・
ストア審査・将来の機能拡張の誘因を抑えるための設計判断**であり、
既存方針（22.2・8.5節）を変更する理由はない。

## 23. 公開プロフィール（YouTubeチャンネル名・アイコンの再利用、Task#134継続）

「公開プロフィールはサーバーなしでは作れないか」という検討に対する結論。
NIARIM独自のプロフィール機能は持たず、投稿時に連携済みのYouTube
チャンネルが持つ公開情報をそのまま再利用する方式（選択肢B）を採用する。

### 23.1 方針

NIARIM独自の「プロフィール編集」画面（ニックネーム変更・自己紹介文・
任意のアイコン画像アップロード等）は作らない。公開プロフィールとして
表示する名前・アイコンは、連携済みYouTubeチャンネルの公開情報
（チャンネル名・チャンネルアイコン画像URL）をそのまま表示する。

- 自由記述の入力欄を新設しないため、なりすまし・誹謗中傷目的のテキスト
  というUGCリスクの種を増やさない
- チャンネル名・アイコンはすでにYouTube上で公開済みの情報であり、
  NIARIM側で新たな個人情報を収集・管理する必要がない
- サーバー側で保存するのはチャンネル名・アイコンURLの文字列のみ
  （5章のメタデータに追加、動画メタデータと同様2KB以内に収まる軽量な
  情報。画像ファイル自体はNIARIM側で再ホストしない）

### 23.2 取得タイミングとYouTube APIクォータへの影響

チャンネル名・アイコン取得には`channels.list`（`part=snippet`）を使う。
これは10章の統計取得・投稿とは別枠の、通常の共有クォータ（1回1ユニット
程度）に属する軽量な呼び出しである。

このAPIは「作品カードを表示するたびに」といったライブ取得では**呼ばない**。
以下のタイミングでのみ呼び出し、結果をNIARIM側のメタデータ
（DynamoDB）にキャッシュする。

- 初回のYouTube連携時（3章の「投稿先チャンネル確認」ステップ。もともと
  発生する予定だった呼び出しであり、公開プロフィールのために新たに
  追加する呼び出しではない）
- 作品投稿時（キャッシュを最新化。投稿頻度は11章の上限により1ユーザー
  1日最大数件）

作品一覧・作品詳細・ランキングなど、他のユーザーが公開プロフィールを
閲覧する場面では、すべてNIARIM側にキャッシュ済みの文字列を表示する
だけであり、閲覧のたびにYouTube APIを呼び出すことはない。

したがって、公開プロフィール機能を追加しても、YouTube APIクォータの
消費は「連携・投稿のタイミングで1回1ユニットが追加される」程度に
とどまる（11章の投稿上限により最大でも1ユーザー1日数件）。閲覧側
（他ユーザーが作品を見る回数）に比例して増えることはなく、実質的な
増分はごくわずかである。

### 23.3 実装時の注意

- 5章のメタデータ表に`channelName`・`channelAvatarUrl`（＋キャッシュ
  取得日時）を追加する
- アイコン画像自体はNIARIM側で再ホストせず、YouTube側のURLをそのまま
  参照する（NIARIM側で画像ファイルを保存・配信しない方針を維持）
- ユーザーがYouTube側でチャンネル名・アイコンを変更した場合、次回投稿時
  まではNIARIM側の表示が更新されない（キャッシュのため）。即時反映が
  必要になった場合は「プロフィール情報を更新」ボタン等での明示的な
  再取得を将来検討する
- これは「一覧化・被参照数の可視化」を伴わない一方向の表示情報に
  すぎず、22章で整理した届出義務の境界線には影響しない
