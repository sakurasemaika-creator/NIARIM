# 29_動画投稿・ランキング機能仕様

現時点では仕様検討段階であり、コード実装には未着手。AWS・Google Cloud側の
アカウント整備、OAuth審査など、このリポジトリの外側の前提条件が整ってから
着手する。

## 1. 基本方針

NIARIMは作品動画そのものを自前で保存・配信しない。動画のホスティング先は
YouTubeに限定し、NIARIM側は動画のメタデータのみを保持する。

```text
NIARIM → YouTubeへ動画投稿 → YouTube上に動画を保存・配信
NIARIMには動画のメタデータ（動画ID・再生数等）だけ保存
```

ニコニコ動画・TikTok等、YouTube以外への投稿選択肢は対象外とする（再生数・
高評価数・コメント数の取得元をYouTube 1本に統一し、ランキング計算を単純化
するため）。

## 2. YouTube連携フロー

投稿の都度ではなく、事前にYouTubeアカウント／チャンネルをNIARIMと連携して
おく方式にする。

```text
初回：NIARIM →「YouTubeと連携」→ Googleアカウント認証 → 投稿先チャンネル確認 → 連携完了
以後：作品完成 → NIARIMで「YouTubeに投稿」→ 連携済みチャンネルへ投稿
      → YouTube動画ID取得 → NIARIMに作品登録
```

## 3. NIARIM側で保存するデータ（動画ファイル自体は保存しない）

| 項目 | 用途 |
|------|------|
| NIARIM作品ID / NIARIMユーザーID | 作品・投稿者の識別 |
| YouTubeチャンネルID / YouTube動画ID | YouTube側との紐付け、投稿判定（4章） |
| 動画タイトル・投稿日時・YouTube URL・サムネイル情報 | 一覧・詳細表示 |
| 再生回数・高評価数・コメント数 | ランキング・詳細表示 |
| 最終取得日時 | 統計の鮮度管理 |
| デイリー／週間／月間／年間ランキング用データ | 期間別ランキング算出 |

## 4. NIARIM投稿作品であることの判定（持ち込み禁止）

概要欄の文字列やハッシュタグ（例：`#NIARIM`）はユーザーが自由に付けられて
しまうため判定に使えない。**NIARIMからYouTubeへ投稿した時点で取得した
YouTube動画IDのみをDBへ登録する**方式とし、既存のYouTube動画（既に大量
再生されている動画等）を後から持ち込んでランキングに登録することを技術的
に不可能にする。

## 5. 統計値の扱い

再生回数・高評価数・コメント数はYouTube側の値をそのまま表示し、NIARIM側で
独自に加算・合算しない（例：YouTube 125,430再生にNIARIM独自カウントを
足して127,430と表示する、といったことはしない）。高評価・コメント機能も
NIARIM内には実装せず、YouTube側の機能に一本化する。

## 6. ランキング

累計／年間／月間／週間／デイリーの5種類。トップN件のみでなく**登録作品を
全件対象**とする（過去の作品が後から急に伸びるケースを正しく拾うため）。

新着順は、ランキングとは別に、NIARIM DB内の投稿日時のみで表示できる
（表示のためにYouTube APIを呼ぶ必要はない）。

同一作者の作品一覧は、NIARIMユーザーID・YouTubeチャンネルID・YouTube動画ID
の関連付けから導出する。

## 7. YouTube Data API の利用

統計取得には`videos.batchGetStats`を使う。

| メソッド | クォータ | 備考 |
|---------|---------|------|
| `videos.batchGetStats` | 専用バケットで10,000ユニット/日（1回1ユニット） | 2026年6月3日追加。他メソッドとは別枠。統計の一括取得用途 |
| `videos.insert`（動画投稿） | 専用バケットで100ユニット/日（1回1ユニット＝1日100件まで） | 2025年12月ごろに約1,600ユニット→約100ユニットへ引き下げ済み。**統計取得用クォータとは完全に別枠**。プロジェクト全体で1日の投稿数の実質上限になるため、ユーザー数が増えて超過見込みが立った時点でGoogleへのクォータ増枠申請（審査あり）が必要 |

上記2点はGoogle公式ドキュメントで裏取り済み（2026年8月時点）。

## 8. ランキング更新頻度

1日2〜4回を選択できる設計にし、初期運用は負荷を見ながら決定する。システム
自体は1日4回更新に対応できる構成にしておく。

## 9. インフラ構成

```text
NIARIM App
  │ YouTube連携・投稿（OAuth、videos.insert）
  ↓
YouTube（動画本体・再生・高評価・コメント）
  │ 動画ID・統計（videos.batchGetStats）
  ↓
DynamoDB（作品メタデータ・作者情報・YouTube動画ID・統計・ランキング情報）
  ↑
Lambda ← EventBridge Scheduler（定期実行）
```

- DB：Amazon DynamoDB（サーバーレス、無料枠25GBストレージ／25 WCU／25 RCU）。
  動画を保存しないため、1作品10KB換算でも概算250万作品分の余裕がある
  （インデックス等のオーバーヘッドは別途考慮が必要な概算値）。
- バッチ処理：AWS Lambda（統計取得・ランキング再計算）。
- 定期実行：Amazon EventBridge Scheduler（無料枠は月1,400万回呼び出し、
  期間限定トライアルではなく恒久的な無料枠）。1日4回runでも月間呼び出し数は
  この枠に対して極めて小さい。

## 10. 未解決・着手前に要対応の項目

このセクションはGPTが提示した案をレビューした際に見つかった、着手前に
決めておく必要がある論点。

1. **アプリ⇄バックエンドのAPI層が未設計**：DynamoDB・Lambda・EventBridge
   Schedulerの構成図だけでは、NIARIMアプリが「投稿情報をDBへ登録する」
   「ランキング・新着一覧を取得する」経路が無い。API Gateway＋Lambda、また
   はLambda Function URL等でREST API層を別途設計する必要がある。
2. **`videos.insert`の投稿クォータ**：7章のとおり、統計取得用クォータとは
   別に投稿自体に1日100件（プロジェクト全体）の上限がある。ユーザー数の
   増加見込みに応じて増枠申請の計画を立てておく。
3. **YouTube OAuthスコープの審査**：`youtube.upload`のような制限付き
   スコープを一般公開アプリで使うにはGoogleのアプリ確認審査が必須。
   利用規約・プライバシーポリシーの提示や説明動画の提出が必要で、数週間
   かかることがある。想定ユーザー数次第ではセキュリティ評価（CASA）が
   追加で必要になる可能性がある。
4. **ストアのUGCポリシー対応**：アプリ内にユーザー投稿動画のランキング・
   新着一覧を表示することは、App Store／Google PlayのUGC
   （ユーザー生成コンテンツ）ガイドラインの対象になる。通報・ブロック
   機能や運営による削除導線が必要で、`license_screen.dart`・プライバシー
   ポリシー画面側の記載更新も合わせて必要になる見込み。
5. **大規模化時のDynamoDB設計**：初期規模（数千〜数万作品）であれば
   「Lambdaで全件スキャン→ソート」で問題ないが、数十万作品規模になった
   場合はスコア順にソートされたGSI（グローバルセカンダリインデックス）
   設計を検討し、全件スキャンからの移行コストを避けておく。
6. **このリポジトリはバックエンドを一切持たない**：現状のNIARIMは全機能が
   端末ローカル完結（SharedPreferences・ローカルファイル保存）であり、
   本機能が初めてのサーバーサイド実装になる。AWS／Google Cloudの
   アカウント整備、IaC（CDK/Terraformなど）、認証情報の安全な管理を
   新規に立ち上げる必要がある。
