# 29_動画投稿・ランキング機能仕様

現時点では仕様検討段階であり、コード実装には未着手。AWS・Google Cloud側の
アカウント整備、OAuth審査など、このリポジトリの外側の前提条件が整ってから
着手する。本章の内容は複数回のレビューを経た確定仕様。

## 1. 基本方針

NIARIMは作品動画そのものを自前で保存・配信しない。動画のホスティング先は
YouTubeに限定し、NIARIM側は動画のメタデータのみを保持する。

```text
NIARIM → YouTubeへ動画投稿 → YouTube上に動画を保存・配信
NIARIMには動画のメタデータ（動画ID・再生数等）だけ保存
```

ニコニコ動画・TikTok等、YouTube以外への投稿選択肢は対象外とする（再生数・
高評価数・コメント数の取得元をYouTube 1本に統一し、ランキング計算を単純化
するため）。

## 2. ログイン要否

「アニメを描いて遊ぶだけ」のユーザーにログインを要求しない一方、他の
ユーザーを識別する必要がある操作（投稿・通報・ブロック）だけGoogle認証を
要求する。

| 機能 | ログイン |
|------|---------|
| アニメ制作・端末内保存 | 不要 |
| みんなの作品を見る／新着／ランキング | 不要 |
| 作者の作品一覧を見る | 不要 |
| YouTube投稿 | **必須** |
| 作品の通報 | **必須** |
| ユーザーのブロック | **必須** |

通報・ブロックをログイン必須にすることで、匿名IDによるなりすまし連投を
防ぎ、かつ運営側が「誰が通報したか」を識別できるようにする。

## 3. YouTube連携・投稿フロー

投稿の都度ではなく、事前にYouTubeアカウント／チャンネルをNIARIMと連携して
おく方式にする。

```text
初回：NIARIM →「YouTubeと連携」→ Googleアカウント認証 → 投稿先チャンネル確認 → 連携完了
以後：作品完成 → NIARIMで「YouTubeに投稿」→ 連携済みチャンネルへ投稿
      → YouTube動画ID取得 → NIARIMに作品登録
```

`youtube.upload`スコープ（YouTube動画の管理権限）を使用する。公開前に
Googleのアプリ確認審査が必要になるため、実装より前に着手すべき別タスクと
して扱う（9章）。

Google OAuthはYouTubeチャンネルへの投稿権限を取得するために使うものであり、
NIARIM独自のユーザーアカウント基盤とは別物として設計する（4章）。将来
YouTube以外の投稿先やNIARIM独自アカウントへ拡張する余地を残すため。

## 4. NIARIM User IDの発行・紐付け

Googleアカウントのメールアドレス等をそのままNIARIMの公開プロフィールとして
使わない。GoogleのIDトークンに含まれる`sub`（アカウント固有の安定した識別子）
をキーとして、NIARIM User ID（ランダムなUUID等）を発行・参照する。

```text
初回投稿時：Google sub → 未登録 → NIARIM User ID発行（例：N000001）
再訪問時　：Google sub → 既存ユーザー → 発行済みのN000001を再利用
```

これにより、再インストール・機種変更・複数端末の利用があっても同一の
NIARIM User IDに紐付けられ、投稿履歴や作者別作品一覧が分断されない。

## 5. NIARIM側で保存するデータ（動画ファイル自体は保存しない）

1作品あたりのメタデータは2KB以内に収める方針とする（動画本体・画像本体・
音声本体はDynamoDBに保存しない）。

| 項目 | 用途 |
|------|------|
| NIARIM作品ID（workId） / NIARIM User ID | 作品・投稿者の識別 |
| YouTubeチャンネルID / YouTube動画ID（youtubeVideoId） | YouTube側との紐付け、投稿判定（6章）、冪等登録キー（14章） |
| 動画タイトル・投稿日時・YouTube URL・サムネイル情報 | 一覧・詳細表示 |
| 再生回数・高評価数・コメント数・rankingScore | ランキング・詳細表示（8章） |
| 最終取得日時 | 統計の鮮度管理 |
| 通報情報（対象作品ID・通報者のNIARIM User ID・理由・日時・対応状況） | UGC対応（9章） |
| ブロック関係（ブロック元／先のNIARIM User ID） | UGC対応（9章） |

2KB×50万作品で概算約1GB（GSI分のオーバーヘッドを別途見込む必要はあるが、
DynamoDB無料枠の25GBに対して十分余裕がある規模）。

## 6. NIARIM投稿作品であることの判定（持ち込み禁止）

概要欄の文字列やハッシュタグ（例：`#NIARIM`）はユーザーが自由に付けられて
しまうため判定に使えない。**NIARIMのバックエンドが投稿処理の成功時に受け
取ったYouTube動画IDのみをDBへ登録する**方式とし、既存のYouTube動画（既に
大量再生されている動画等）を後から持ち込んでランキングに登録することを
技術的に不可能にする。

## 7. 統計値の扱い

再生回数・高評価数・コメント数はYouTube側の値をそのまま表示し、NIARIM側で
独自に加算・合算しない。高評価・コメント機能もNIARIM内には実装せず、
YouTube側の機能に一本化する。

## 8. ランキング・新着・作者別一覧

累計／年間／月間／週間／デイリーの5種類。表示はいずれもTop 50のみ。

### 8.1 統計更新バッチ（全作品対象）

過去の作品が後から急に伸びるケースを正しく拾うため、統計更新は登録作品を
**全件対象**とする。

```text
DynamoDBを1ページずつScan
  → 各作品のYouTube動画IDをvideos.batchGetStatsへ渡して統計取得
  → rankingScoreを計算
  → 各作品のrankingScore等を更新
```

50万件規模のScanは1回のLambda実行（最大15分）には収まらないため、以下の
方式でページ単位に分割する（Step Functionsは使わず、現行のLambda +
DynamoDB + EventBridge構成のまま完結させる）。

- EventBridge Schedulerは更新サイクルの開始のみをトリガーする。
- Lambdaは1ページ分（DynamoDB Scanの1回のレスポンス分）を処理したら、
  `LastEvaluatedKey`をペイロードに載せて**自分自身を非同期呼び出し
  （`InvocationType=Event`）**し、そのまま終了する。次の呼び出しが続きの
  ページから処理を再開する。
- 無限ループ事故を防ぐため、想定作品数から逆算した最大反復回数のガードを
  入れる。
- Lambdaの非同期呼び出しは失敗時にAWSが自動リトライすることがあるため、
  同一ページが二重に処理される可能性がある。`rankingScore`の更新は
  「最新値で上書き」なので二重処理されても結果は壊れない（冪等）。
- 全ページの処理が完了したら、DynamoDBに「最終更新完了日時」を1件記録する。
  表示側（8.2のGSI Query）が更新途中の中途半端な状態を参照しないよう、
  更新完了後にまとめて反映される設計にする。

統計更新に使う読み取り量はDynamoDBの無料枠（25 RCU）を使い切らないよう、
15〜20 RCU程度に抑え、残りを通常利用（閲覧・投稿等）に残す。

### 8.2 ランキング表示（Top 50のみ、GSIを使用）

8.1とは別の処理として扱う。**Top 50を出すためだけに全件Scanは行わない。**
8.1で各作品のrankingScoreを更新する際に、DynamoDBのGSI（rankingScoreを
ソートキーに持つ）へも書き込んでおき、表示時はこのGSIへのQuery1回
（降順・上限50件）で完結させる。

```text
[統計更新] 全作品 → YouTube統計取得 → rankingScore更新（GSIにも反映）
[表示]     GSI Query（rankingScore降順・Top 50） → アプリ
```

現状の想定成長ペース（10章：1日最大100投稿）では、GSIの書き込み集中
（ホットパーティション）が問題になる水準には当面到達しない見込み。将来
作品数・投稿頻度が大きく増えた場合は、GSIのパーティションキーを分割
（シャーディング）する設計への移行を検討する（17章）。

### 8.3 新着表示

ランキングとは別に、NIARIM DB内の投稿日時のみで表示できる（表示のために
YouTube APIを呼ぶ必要はない）。

### 8.4 同一作者の作品一覧

NIARIM User ID・YouTubeチャンネルID・YouTube動画IDの関連付けから導出する。

## 9. UGC（ユーザー生成コンテンツ）対応

NIARIM内の新着・ランキング・作者別作品一覧で他ユーザーの投稿作品を見せる
以上、ストアのUGCポリシー対象として設計する（動画本体をNIARIMがホスト
していないことは免除理由にならない。Google Playだけでなく、将来iOS版を
出す場合はAppleのガイドライン1.2も対象になる）。最低限、以下をアプリ内
機能として用意する。

- **作品を報告**（ログイン必須）：作品詳細画面から通報を送信し、NIARIM側
  DBに通報者のNIARIM User ID付きで保存する（5章）。運営が確認し、問題が
  あればNIARIM内の一覧から除外する（YouTube側の動画自体は削除しない。
  除外はNIARIM内の掲載可否のみを指す）。
- **ユーザーをブロック**（ログイン必須）：ブロックした相手の作品をNIARIM内
  の一覧・ランキングから自分に対して非表示にする。
- **運営対応の記録**：通報の対応状況（未対応／確認中／対応済み）をDB上で
  追跡できるようにする。
- 通報者を識別できるため、実装時には同一ユーザーからの連続通報に対する
  簡易なレート制限も入れておく（17章）。

YouTube動画自体に問題がある場合は、YouTube側の報告機能の利用も別途案内する。

## 10. YouTube Data API のクォータと投稿上限

統計取得には`videos.batchGetStats`を使う。

| メソッド | クォータ | 備考 |
|---------|---------|------|
| `videos.batchGetStats` | 専用バケットで10,000ユニット/日（1回1ユニット） | 2026年6月3日追加。他メソッドとは別枠。統計の一括取得用途 |
| `videos.insert`（動画投稿） | 専用バケットで100ユニット/日（1回1ユニット＝1日100件まで） | 2025年12月ごろに約1,600ユニット→約100ユニットへ引き下げ済み。**統計取得用クォータとは完全に別枠** |

上記はGoogle公式ドキュメントで裏取り済み（2026年8月時点）。

NIARIM側でも**1日最大100作品**を投稿上限として仕様化する（YouTube側の
デフォルトクォータを前提にし、増枠を前提にしない）。101件目以降の投稿は
「本日の投稿上限に達しました。翌日以降に再度お試しください。」と案内し、
日次カウンターで管理する。この上限はNIARIM全ユーザー共有の枠である点に
注意する（1ユーザーあたりではない）。

将来クォータが問題になるほど成長した場合は、その時点でGoogleへの増枠申請
を検討する（承認される保証はないため、増枠に依存しない設計を初期仕様の
前提とする）。

### 統計更新の呼び出し数試算（100件ずつ取得する場合）

| 作品数 | 1回の更新あたりcall数 | 1日1回 | 1日2回 | 1日3回 | 1日4回 |
|-------|--------------------:|------:|------:|------:|------:|
| 10,000作品 | 100 | 100 units | 200 units | 300 units | 400 units |
| 500,000作品 | 5,000 | 5,000 units | **10,000 units** | 15,000 units | 20,000 units |

50万作品規模では、1日2回の更新でデフォルトの10,000ユニット/日にちょうど
到達する。なお1日100投稿の上限（前述）から逆算すると、50万作品への到達
には最大ペースでも約5,000日（約13.7年）を要するため、統計更新頻度の
上限問題（1日2回ライン）に実際に到達するのはかなり先になる見込み。

## 11. ランキング更新頻度

初期は1日2〜4回を選択できる設計にしておき、作品数が増えてきたら1日2回を
基本とする。50万作品規模に到達した場合、1日2回がデフォルトクォータ枠の
上限ライン（10章）。

## 12. YouTube OAuth審査（公開前の必須タスク）

`youtube.upload`スコープは制限付きスコープであり、一般公開アプリで使用する
にはGoogleのアプリ確認審査が必要になる。実装後ではなく、公開前の重要タスク
として次の順で進める。

```text
① Google Cloudプロジェクト作成
② YouTube Data API有効化
③ OAuth同意画面の設定
④ OAuthクライアントの作成
⑤ youtube.uploadスコープの申請理由整理
⑥ テストユーザーでの動作確認
⑦ Googleのアプリ確認審査・公開要件の確認
```

審査には利用規約・プライバシーポリシーの提示、スコープの利用目的を示す
説明動画の提出などが必要で、数週間かかる場合がある。想定ユーザー数次第では
追加のセキュリティ評価（CASA）が必要になる可能性もある。

## 13. バックエンド構成

DynamoDBへアプリから直接アクセスする構成にはしない。API Gatewayは使わず、
**Lambda Function URL**（Lambda関数にHTTPSエンドポイントを直接付与できる
仕組み）をAPI層として採用する（「できる限り無料で運用する」方針を優先）。

```text
NIARIM App
   │ HTTPS
   ▼
Lambda Function URL（AuthType: NONE）
   ▼
1つのLambda内にAPIルーター（method + pathで振り分け）
   ├─ GET  /ranking/daily 等 → ランキング表示（8.2）
   ├─ GET  /works/latest      → 新着表示（8.3）
   ├─ GET  /users/{id}/works  → 作者別作品一覧（8.4）
   ├─ POST /works             → 作品登録（14章）
   ├─ POST /reports           → 通報（要ログイン、9章）
   └─ POST /blocks            → ブロック（要ログイン、9章）
   ▼
DynamoDB

EventBridge Scheduler（1日2〜4回）
   ▼
ランキング更新Lambda（8.1の自己再帰呼び出しでページ分割処理）
   ├→ YouTube API（videos.batchGetStats）
   └→ DynamoDB（統計・rankingScore・GSI更新）
```

Function URLの`AuthType`は`NONE`（AWS認証なしの公開エンドポイント）を使う。
アプリに秘密鍵を埋め込んでAPI認証に使う方式は採用しない（APKやIPAから解析
される可能性があるため）。読み取り系（ランキング・新着等）は匿名利用を
許可し、書き込み系（投稿・通報・ブロック）はNIARIM User ID（4章）を用いた
リクエスト検証・レート制限をLambda側で実装する。API Gatewayの使用量プラン・
WAF等は、将来より高度なAPI管理が必要になった場合の追加候補とする。

## 14. データ整合性（YouTube投稿成功→DB登録失敗の対策）

YouTubeへの投稿自体は成功したが、その後のNIARIM DB登録が通信エラー等で
失敗するケースを想定し、`youtubeVideoId`を冪等キーとして扱う。

```text
① YouTube投稿 → ② videoId取得 → ③ NIARIM DB登録
```

③が失敗した場合はvideoIdを使って再試行する。DB側は「videoIdが既に登録
済みなら更新、未登録なら新規登録」として扱うため、再試行しても同一作品が
二重登録されない。

## 15. 利用規約・プライバシーポリシーへの反映が必要な点

現行の規約・プライバシーポリシーには「本アプリは作成コンテンツを開発者の
サーバーへ送信・収集・同期する機能を提供していません」という趣旨の記述が
ある。本機能を実装すると、この記述はそのままでは不正確になる。

反映時は次の2点を明確に分けて記載する。

- 作品データそのもの（動画ファイル・プロジェクトデータ）はNIARIMのサーバー
  には保存しない（引き続き維持される方針）。
- 公開作品に関するメタデータ（YouTube動画ID・チャンネル識別情報・タイトル・
  統計情報・掲載情報・通報情報等）と、投稿・通報・ブロック機能利用時に
  発行されるNIARIM User IDはNIARIMのサーバー（DynamoDB）で管理する
  （本機能で新たに追加される事実）。

UGC対応（9章：通報・ブロック・運営対応）についても、規約側に利用条件として
明記する。

| 項目 | 方針 |

## 17. 残っている検討事項

1. **GSIのパーティション設計の将来的な見直し**：8.2のGSIは当面（1日最大
   100投稿という成長ペース）問題にならない見込みだが、将来的に投稿頻度が
   大きく増えた場合はパーティションキーのシャーディングを検討する。
2. **認証済み通報の連投対策**：通報がログイン必須になったことでなりすまし
   は防げるが、同一NIARIM User IDからの連続通報に対する簡易なレート制限は
   別途実装する（9章）。
3. **OAuth審査（12章）は未着手**：Google Cloudプロジェクト作成から着手する
   必要がある。
4. **UGC通報・ブロックの運用フロー**：通報後の運営側の確認・対応フローの
   詳細（誰が確認するか、対応SLA等）は未策定。
5. **利用規約・プライバシーポリシーの具体的な文言**：15章の方針に沿った
   実際の条文はまだ書いていない。
6. **このリポジトリはバックエンドを一切持たない**：現状のNIARIMは全機能が
   端末ローカル完結（SharedPreferences・ローカルファイル保存）であり、
   本機能が初めてのサーバーサイド実装になる。AWS／Google Cloudの
   アカウント整備、IaC（CDK/Terraformなど）、認証情報の安全な管理を
   新規に立ち上げる必要がある。
