# 29_動画投稿・ランキング機能仕様

現時点では仕様検討段階であり、コード実装には未着手。AWS・Google Cloud側の
アカウント整備、OAuth審査など、このリポジトリの外側の前提条件が整ってから
着手する。

## 1. 基本方針

NIARIMは作品動画そのものを自前で保存・配信しない。動画のホスティング先は
YouTubeに限定し、NIARIM側は動画のメタデータのみを保持する。

```text
NIARIM → YouTubeへ動画投稿 → YouTube上に動画を保存・配信
NIARIMには動画のメタデータ（動画ID・再生数等）だけ保存
```

ニコニコ動画・TikTok等、YouTube以外への投稿選択肢は対象外とする（再生数・
高評価数・コメント数の取得元をYouTube 1本に統一し、ランキング計算を単純化
するため）。

## 2. YouTube連携フロー

投稿の都度ではなく、事前にYouTubeアカウント／チャンネルをNIARIMと連携して
おく方式にする。

```text
初回：NIARIM →「YouTubeと連携」→ Googleアカウント認証 → 投稿先チャンネル確認 → 連携完了
以後：作品完成 → NIARIMで「YouTubeに投稿」→ 連携済みチャンネルへ投稿
      → YouTube動画ID取得 → NIARIMに作品登録
```

`youtube.upload`スコープ（YouTube動画の管理権限）を使用する。公開前に
Googleのアプリ確認審査が必要になるため、実装より前に着手すべき別タスクと
して扱う（8章）。

## 3. NIARIM側で保存するデータ（動画ファイル自体は保存しない）

| 項目 | 用途 |
|------|------|
| NIARIM作品ID / NIARIMユーザーID | 作品・投稿者の識別 |
| YouTubeチャンネルID / YouTube動画ID | YouTube側との紐付け、投稿判定（4章） |
| 動画タイトル・投稿日時・YouTube URL・サムネイル情報 | 一覧・詳細表示 |
| 再生回数・高評価数・コメント数 | ランキング・詳細表示 |
| 最終取得日時 | 統計の鮮度管理 |
| デイリー／週間／月間／年間ランキング用データ | 期間別ランキング算出（6章のGSI設計対象） |
| 通報情報（対象作品ID・通報者ID・理由・日時・対応状況） | UGC対応（7章） |
| ブロック関係（ブロック元ユーザーID・ブロック先ユーザーID） | UGC対応（7章） |

## 4. NIARIM投稿作品であることの判定（持ち込み禁止）

概要欄の文字列やハッシュタグ（例：`#NIARIM`）はユーザーが自由に付けられて
しまうため判定に使えない。**NIARIMのバックエンドが投稿処理の成功時に受け
取ったYouTube動画IDのみをDBへ登録する**方式とし、既存のYouTube動画（既に
大量再生されている動画等）を後から持ち込んでランキングに登録することを
技術的に不可能にする。

## 5. 統計値の扱い

再生回数・高評価数・コメント数はYouTube側の値をそのまま表示し、NIARIM側で
独自に加算・合算しない（例：YouTube 125,430再生にNIARIM独自カウントを
足して127,430と表示する、といったことはしない）。高評価・コメント機能も
NIARIM内には実装せず、YouTube側の機能に一本化する。

## 6. ランキング

累計／年間／月間／週間／デイリーの5種類。**統計の更新自体は登録作品を
全件対象**とする（過去の作品が後から急に伸びるケースを正しく拾うため）。

ただし全件対象なのは「YouTube統計を取得してDynamoDBを更新する」バッチ処理
の対象範囲であり、**ユーザーへの表示は上位N件のみ**を返す。50万作品規模に
なってもアプリへ50万件送るわけではない。

```text
[統計更新] 全作品 → YouTube統計取得 → DynamoDB更新
[表示]     DynamoDB → ランキング上位N件 → アプリ
```

このため、DynamoDBは「スコア順に並んだ状態で上位N件を安価に取得できる」
アクセスパターンを最初から設計する（例：期間別ランキング値をソートキーに
持つGSIを用意し、各期間のトップNをGSIへのクエリ1回で取得できるようにする）。
全件スキャンしてLambda側でソートする方式は、初期の小規模なら動くが50万件
規模では避ける。

新着順は、ランキングとは別に、NIARIM DB内の投稿日時のみで表示できる
（表示のためにYouTube APIを呼ぶ必要はない）。

同一作者の作品一覧は、NIARIMユーザーID・YouTubeチャンネルID・YouTube動画ID
の関連付けから導出する。

## 7. UGC（ユーザー生成コンテンツ）対応

NIARIM内の新着・ランキング・作者別作品一覧で他ユーザーの投稿作品を見せる
以上、Google PlayのUGCポリシー対象として設計する（動画本体をNIARIMが
ホストしていないことは免除理由にならない）。最低限、以下をアプリ内機能
として用意する。

- **作品を報告**：作品詳細画面から通報を送信し、NIARIM側DBに通報情報として
  保存する（3章）。運営が確認し、問題があればNIARIM内の一覧から除外する
  （YouTube側の動画自体は削除しない。除外はNIARIM内の掲載可否のみを指す）。
- **ユーザーをブロック**：ブロックした相手の作品をNIARIM内の一覧・ランキング
  から自分に対して非表示にする。
- **運営対応の記録**：通報の対応状況（未対応／確認中／対応済み）をDB上で
  追跡できるようにする。

YouTube動画自体に問題がある場合は、YouTube側の報告機能の利用も別途案内する。

## 8. YouTube OAuth審査（公開前の必須タスク）

`youtube.upload`スコープは制限付きスコープであり、一般公開アプリで使用する
にはGoogleのアプリ確認審査が必要になる。実装後ではなく、公開前の重要タスク
として次の順で進める。

```text
① Google Cloudプロジェクト作成
② YouTube Data API有効化
③ OAuth同意画面の設定
④ OAuthクライアントの作成
⑤ youtube.uploadスコープの申請理由整理
⑥ テストユーザーでの動作確認
⑦ Googleのアプリ確認審査・公開要件の確認
```

審査には利用規約・プライバシーポリシーの提示、スコープの利用目的を示す
説明動画の提出などが必要で、数週間かかる場合がある。想定ユーザー数次第では
追加のセキュリティ評価（CASA）が必要になる可能性もある。

## 9. YouTube Data API のクォータ

統計取得には`videos.batchGetStats`を使う。

| メソッド | クォータ | 備考 |
|---------|---------|------|
| `videos.batchGetStats` | 専用バケットで10,000ユニット/日（1回1ユニット） | 2026年6月3日追加。他メソッドとは別枠。統計の一括取得用途 |
| `videos.insert`（動画投稿） | 専用バケットで100ユニット/日（1回1ユニット＝1日100件まで） | 2025年12月ごろに約1,600ユニット→約100ユニットへ引き下げ済み。**統計取得用クォータとは完全に別枠**。投稿数と統計取得回数は独立して考えてよい |

上記はGoogle公式ドキュメントで裏取り済み（2026年8月時点）。

### 統計更新の呼び出し数試算（100件ずつ取得する場合）

作品数が増えるほど、1回のランキング更新あたりの呼び出し数が増える。

| 作品数 | 1回の更新あたりcall数 | 1日1回 | 1日2回 | 1日3回 | 1日4回 |
|-------|--------------------:|------:|------:|------:|------:|
| 10,000作品 | 100 | 100 units | 200 units | 300 units | 400 units |
| 500,000作品 | 5,000 | 5,000 units | **10,000 units** | 15,000 units | 20,000 units |

**50万作品規模では、1日2回の更新でデフォルトの10,000ユニット/日にちょうど
到達する。** 1日4回に増やす場合は20,000ユニットとなり、デフォルト枠を超える
ため、Googleへのクォータ増枠申請が必要になる。

「50万作品でも1日4回なら余裕」という試算は、小規模時点（数千〜1万作品）を
前提にしたものであり、50万作品規模には当てはまらない点に注意する。

## 10. ランキング更新頻度の方針

- 初期（作品数が少ない段階）：1日2〜4回を選択できる設計にしておく。
- 作品数が増えてきたら：1日2回を基本とする。
- 50万作品規模に到達した場合：1日2回がデフォルトクォータ枠の上限ライン。
  4回に増やしたい場合はYouTube側のクォータ増枠を検討する（AWS側のコストが
  問題になるのではなく、YouTube APIのクォータが先に律速する）。

## 11. バックエンド構成

DynamoDBへアプリから直接アクセスする構成にはしない。API Gatewayは現時点
では使わず、**Lambda Function URL**（Lambda関数にHTTPSエンドポイントを直接
付与できる仕組み）をAPI層として採用する。無料optimizedな構成を優先する
NIARIMの方針に合っている。API Gatewayは、将来より高度なAPI管理・認証・
レート制限が必要になった場合の追加候補とする。

```text
NIARIM App
   │ HTTPS
   ▼
Lambda Function URL
   ▼
Lambda
   ▼
DynamoDB（作品メタデータ・ランキング情報・作者情報・報告情報）

EventBridge Scheduler（定期実行）
   ▼
Lambda（統計取得バッチ）
   │
   ├→ YouTube API（videos.batchGetStats）
   └→ DynamoDB（統計・ランキング更新）
```

### APIエンドポイント例（Lambda Function URL経由）

| エンドポイント | 用途 |
|--------------|------|
| `POST /works` | 作品登録（YouTube投稿成功後にNIARIM DBへ登録） |
| `GET /works/latest` | 新着作品一覧 |
| `GET /ranking/daily` `/weekly` `/monthly` `/yearly` `/all-time` | 期間別ランキング上位N件 |
| `GET /users/{id}/works` | 指定作者の作品一覧 |
| `POST /reports` | 作品の通報登録（7章） |
| `POST /blocks` | ユーザーのブロック登録（7章） |

## 12. 利用規約・プライバシーポリシーへの反映が必要な点

現行の規約・プライバシーポリシーには「本アプリは作成コンテンツを開発者の
サーバーへ送信・収集・同期する機能を提供していません」という趣旨の記述が
ある。本機能を実装すると、この記述はそのままでは不正確になる。

反映時は次の2点を明確に分けて記載する。

- 作品データそのもの（動画ファイル・プロジェクトデータ）はNIARIMのサーバー
  には保存しない（引き続き維持される方針）。
- 公開作品に関するメタデータ（YouTube動画ID・チャンネル識別情報・タイトル・
  統計情報・掲載情報・通報情報等）はNIARIMのサーバー（DynamoDB）で管理する
  （本機能で新たに追加される事実）。

UGC対応（7章：通報・ブロック・運営対応）についても、規約側に利用条件として
明記する。

## 13. 対応状況まとめ

| 項目 | 方針 |
|------|------|
| API層 | Lambda Function URLを採用（API Gatewayは現時点では不使用） |
| DB | DynamoDB |
| バッチ | Lambda |
| 定期実行 | EventBridge Scheduler |
| YouTube OAuth | 公開前にGoogleのアプリ確認審査を実施（8章） |
| `youtube.upload` | 使用予定 |
| UGC対応 | 該当する前提で設計。報告・ブロック・運営対応を実装（7章） |
| 動画持ち込み | 不可。NIARIM経由の投稿のみ登録可能（4章） |
| 動画本体の保存先 | YouTube（NIARIM側はメタデータのみ） |
| ランキング統計更新 | 全作品を対象 |
| ランキング表示 | 上位N件のみをアプリへ返す |
| DynamoDBのGSI設計 | 最初から設計する（6章） |
| `videos.batchGetStats` | 採用。50万作品規模では1日2回がデフォルト枠の目安（9章） |
| 初期のランキング更新頻度 | 1日2〜4回（10章） |
| 利用規約・プライバシーポリシー | メタデータ保存・UGC対応を追記が必要（12章） |

## 14. 未解決・着手前に要対応の項目

1. **GSI設計の詳細**：パーティションキー・ソートキーの具体的な設計（期間別
   ランキング値をどう持つか）はまだ決まっていない。実装時に詳細設計が必要。
2. **YouTube投稿クォータ（1日100件）とユーザー数の関係**：ユーザー数が
   増えて1日100件の投稿上限に近づいた場合の増枠申請計画は未策定。
3. **OAuth審査（8章）は未着手**：Google Cloudプロジェクト作成から着手する
   必要がある。
4. **UGC通報・ブロックの運用フロー**：通報後の運営側の確認・対応フローの
   詳細（誰が確認するか、対応SLA等）は未策定。
5. **利用規約・プライバシーポリシーの具体的な文言**：12章の方針に沿った
   実際の条文はまだ書いていない。
6. **このリポジトリはバックエンドを一切持たない**：現状のNIARIMは全機能が
   端末ローカル完結（SharedPreferences・ローカルファイル保存）であり、
   本機能が初めてのサーバーサイド実装になる。AWS／Google Cloudの
   アカウント整備、IaC（CDK/Terraformなど）、認証情報の安全な管理を
   新規に立ち上げる必要がある。
