# NIARIM FCM プッシュ通知: 運用・実機確認

作品広場のベルで開く通知履歴と端末のプッシュは、サーバーが記録したイベントを使う。送信に失敗しても、保存済みの履歴や操作結果は残る。投稿した端末では、サーバーからの登録完了応答でもOS通知を表示できる。

| 通知のきっかけ | 受け取る人 | 通知を開いたとき |
| --- | --- | --- |
| 通常投稿を正常に登録・公開 | 投稿者 | 自分の作品一覧または公開した作品の詳細 |
| 予約作品をYouTubeで実際に公開、または掲載を正常に切り替え | 投稿者 | 対象作品の詳細 |
| 新しいミッション達成 | 達成した本人 | ミッション一覧 |

フォロー・ブックマーク・リポストの個別通知は、作成・プッシュ配信・アプリ内履歴への返却を終了した。これらの操作と集計は継続する。通常投稿・公開の通知行は30日で期限切れになる。

「設定 → この端末のプッシュ通知」か、作品広場のベルで開く通知一覧の歯車から同じ設定画面に入れる。投稿・公開のプッシュ通知を個別に切り替えられる。スイッチはこの端末のOS通知に適用され、アプリ内の履歴は引き続き読める。全体をオフにすると端末のFCM登録を解除する。Androidの通知許可も必要。予約投稿の受付と、予定時刻以降に実際の公開を確認したことは別々に通知する。

## AWS と Firebase

- AWS 東京リージョンの `niarim-api` が DynamoDB Streams から確定したイベントを処理する。通知履歴を先に保存し、通知行の条件付き更新で同じ配信の重複試行を防ぐ。履歴を記録する段階の一時的なエラーは再試行する。FCM送信を始めた後は結果不明でも再送しない。
- 予約公開LambdaはYouTubeで公開を確認したデータだけを更新する。送信は既存の `niarim-api` の実行ロールで行い、公開LambdaへFirebase権限を追加しない。
- Google CloudのWorkload Identity Federationと送信用サービスアカウントを使う。秘密鍵ファイルは不要。新しい端末登録は最新のアカウントへ結び直し、新しいAPKだけが投稿・公開のデータメッセージを受け取り、端末で表示する。旧APKでのミッション通知の配信は維持する。
- `backend` の型検査・テスト・CDK合成とデプロイ差分を確認してから、`dev_branch` の Backend CI のデプロイ手順を使う。稼働中の特典・料金・Google/SNS設定をデプロイで戻さない。テーブル名と実行ロールは既存リソースを維持する。
- デプロイ後は、既存テーブルの `NEW_AND_OLD_IMAGES`、イベントソースの稼働、ワーカー有効フラグ、FCM認証エラーの有無を確認する。設定が揃っていることはGoogle認証や端末への配信成功を意味しない。

## Galaxyでの最終確認

最新の `dev_branch` APKをテスト端末に入れ、通知許可をオンにして受け手と操作側の別テストアカウントを使う。個人情報、FCMトークン、Google認証情報を画面やログへ残さない。

1. 別のテストアカウントでフォロー、公開作品のブックマーク、リポストを行う。受け手のOS通知・作品広場の履歴に個別通知が表示されず、各操作・集計は更新されることを確認する。
2. 通常投稿の登録と公開切り替えを試す。予約作品では、予約受付と実際の公開確認が別の日時で届くことを確認する。ミッションでは新規達成一件だけを使って既存のタップ先も再確認する。
3. 2つの入口と戻り先を確認する。投稿・公開の通知をオフにし、そのOS通知が止まってアプリ内の履歴は残ることを確認する。再度オンにした新規イベントと、アプリ終了状態からのタップも確認する。
4. 受信しないときは Android許可・端末登録・履歴作成・AWSからGoogleの認証・FCM受付・OS表示の段階を分け、実際に通った段階だけを記録する。
